### 失败链路（今天最有价值的一段记录）

| 错误码 | 含义 | 根因 |
|---|---|---|
| `-601034` | 没有权限，请先开通云开发 | 云开发未开通 |
| `-501000` | `FunctionName parameter could not be found` | 云函数未部署 |

### 平台状态冲突（非错误码类）

| 现象 | 含义 | 处理 |
|---|---|---|
| `当前函数处于Updating状态，无法进行此操作` | 云函数正在被更新（通常是刚部署完），此时改配置会冲突 | 等 30–60 秒 → 刷新 → 确认状态为「已部署」→ 再改配置。**顺序：先部署代码，等状态稳定，再改配置** |

### 今日最重要的技术发现

**内存仓储与云数据库存在 5 类语义差异，且内存那套"更宽松"，导致本地全绿、线上必挂。**

| # | 差异点 | 内存实现 | 云数据库 | 修法 |
|---|---|---|---|---|
| 1 | 查询谓词 | 支持函数谓词 | 只支持结构化操作符 | 云实现主动抛错，禁止函数谓词 |
| 2 | `exists` 语义 | 认为 `null` 不存在 | `null` 也算存在 | 对齐 MongoDB `$exists` |
| 3 | 对象字段写入 | 整体替换 | **合并语义** | 禁止向 `null` 写对象；聚合体存 JSON 字符串 |
| 4 | 建集合 | 按需自动 | **必须先建，否则 `-502005`** | `ensureCollection` + `ops.initDb` 显式创建 |
| 5 | 唯一约束 | （原先未实现） | 由索引强制 | 内存按 `lib/repo/indexes.js` 登记表模拟 |

**结论：单元测试通过 ≠ 系统可运行。** 两者的差异必须被当作**一类需要显式管理的风险**，
而不是当作意外。这就是「工程能启动」必须单列为一条验收标准的原因。

**处置办法**：新增 `ops.selfTest`（实测九种写入形态）与 `ops.verifyIndexes`
（故意写重复数据，验证唯一索引是否真的在拦）。两都可重复执行，结果可归档。

### 三项待确认事实的实测结论

| 待确认 | 结论 | 依据 |
|---|---|---|
| 坐标系 | ✅ **GCJ-02 一致** | polyline 首点 `45.775524, 126.617213` 与输入相差约 25 米 |
| `distance` 单位 | ✅ **米** | 815 与两点实际距离量级吻合 |
| **`duration` 单位** | ⚠️ **分钟，不是秒** | 815 米返回 12 → 按分钟 68 米/分（合理）；按秒 4075 米/分（荒谬） |

**`duration` 单位错误是首版代码的实际 bug**：写成 `durationSeconds / 60`，会把每段步行时间算成实际的 **1/60**，
规划器的可行性检查会全部误判为"时间充裕"。**这类"数值算错但不报错"的缺陷，正是 `map.probe` 存在的意义。**

修法不是把结论写死，而是**自检**：用"隐含速度是否落在合理步速区间"当场判定单位，
并把判定依据随结果返回（`unitCheck`），任何一次调用都能自我复核。

### 顺带验证的两条设计假设

**① `DETOUR_FACTOR = 1.3` 的校准情况**

| 场景 | 直线距离 | 实际步行 | 倍数 |
|---|---|---|---|
| 中央大街 → 防洪纪念塔 | 605 米 | **815 米** | **1.35** ✅ 估值准确 |
| 起点 → 旁边 10 米 | 10 米 | **76 米** | **7.6** ❌ 完全不可靠 |

**结论**：直线估算在正常距离下可用（误差可接受），**短距离下必须用真实路线**——
这正好论证了 `lib/geo.js` 的设计：**真实接口优先，直线估算只作地图不可用时的兜底**。

**② `polyline` 是差分压缩格式**

首对为绝对坐标，其后为相对前一点的增量（含 `0,0` 占位），**需按官方文档解码**。
`steps[].polyline_idx` 给出每段的索引区间，是解码的钥匙。
**但核心功能不依赖它**——集合推荐只需要 `distance` + `duration`，地图上画起终点连线即可。

## 发现：规划器从未调用地图接口（用户发现）

**现象**：行程页生成路线后，5 个节点显示「**854 分钟步行**」，明显不合理。

**排查**：追调用链

```
trip.plan → timeline.buildTimeline → geo.walkMinutes(prevPlace, place, params)
                                          ↓
                              只用 place.walkableTo（踏勘缓存）
                              没有 → 直线距离 × 1.3 ÷ 75
```

**根因**：`geo.walkMinutes` 只有两条路径 —— 踏勘缓存 与 直线估算，
**从不调用地图步行路线接口**。于是当天花一整天调通的接口，
在规划器里**一次都没被用到**，"根据路况计算"名不副实。

**这是一类特别难发现的缺陷**：功能"看起来能用"（有数字、有时间线、页面正常），
只是数字来源不对。107 项单元测试全绿，因为测的是"有没有回落"，
而没测"该不该回落"。

**修正**：

1. `lib/geo.js` 增加第三来源：`WALK_SOURCE = { SURVEY, UPSTREAM, ESTIMATED }`
   —— 三态**必须可区分**，旧的 `measured` 拆成前两者。
2. `trip.plan` 在调用**同步的**时间线计算之前，先把缺失路段从地图接口取回来
   （`fillMissingWalkTimes`），写进 `placesById.walkableTo` 并**落库缓存**。
3. 三级优先：踏勘实测 → 地图接口 → 直线估算；**取不到时不写缓存**
   （否则一次估算会变成永久事实）。
4. 响应新增 `walkTimes`：来源构成、失败段明细、地图调用次数、来源含义。
5. 节点下发坐标（画游览顺序连线用）与 `travelSource`（界面标注"估算"用）。

**顺带修正**：首版把核验做成了"全有或全无"，导致地点检索回来的 POI
一个都用不了 —— 已按用途拆成 `canBeTripNode` / `canBeMeetingPoint` 两级。

**教训**：**"能跑"和"跑的是不是那条路"是两件事。**
一个子系统调通之后，必须显式确认它在**真正的主链路**上被调用过 ——
否则会出现"接口很健康，但没人用它"。

## 发现：简称匹配被"名字里嵌了地标"的 POI 骗到（用户发现）

**现象**：输入「我想去冰雪大世界」，系统给出

```
必去：哈尔滨悦苒民宿(哈尔滨冰雪大世界融创文旅城龙川路地铁站)
检索词：哈尔滨悦苒民宿(哈尔滨冰雪大世界融创文旅城龙川路地铁站)
搜索结果：1 个（直线 10178 米）
```

**根因**：`matchKnown` 为了认简称写成了双向包含
（`text.includes(n) || n.includes(text)`），而库里有一条早先检索回来的 POI，
它的名字里**嵌了「哈尔滨冰雪大世界」**：

```js
'哈尔滨悦苒民宿(哈尔滨冰雪大世界融创文旅城龙川路地铁站)'.includes('冰雪大世界')
// → true  ❌
```

于是：**一间民宿被当成了用户要去的地方**，检索词变成那串 30 字全名，
搜出来只有它自己。三处错误级联。

**修正**：简称只在**长度接近**时才认（用户的说法至少覆盖全名一半）
```
「索菲亚」→「圣索菲亚教堂」      3/6 = 0.5  ✓ 仍认得
「冰雪大世界」→ 那条民宿名      5/30 ≈ 0.17 ✗ 拒绝
```

**顺带补上「去 X」目标抽取** —— 用户说的地标常常不在已知库里
（「我想去冰雪大世界」就是），但那句话的意思再清楚不过。
不加这一步，这类输入会**什么都搜不到**。并列结构要拆开
（「想去教堂和公园」→ 检索"教堂"，"公园"记入 `goalAlternatives`）。

**教训**：**匹配规则放宽一寸，误判就多一类。**
双向包含看起来只是"多容忍一种写法"，实际是把"用户提到了某个地方"
偷换成了"某段文字是某个长名字的子串"—— 这是两回事。
凡是放宽匹配的地方，都要同时想清楚**它会误命中什么**。

## 发现：同一个 bug 犯了两次 —— 因为我用自己编的数据测自己写的规则

**第一次**（2026-10-13 下午）：用户搜「我想去冰雪大世界」，检索词变成
「冰雪大世界[地铁站]」。根因是库里一条 POI 的类目是
`基础设施;交通设施:地铁站`，它是地铁站不是景点。
修法：加 `NON_VISITABLE_CATEGORY_RE` 排除交通设施。测试用
`基础设施;交通设施:地铁站` 断言 —— **绿了**。

**第二次**（同日晚）：用户再搜，检索词变成「冰雪大世界**[公交站]**」。

真实类目是 `基础设施;交通设施:公交车站`，而正则里写的是「公交站」：

```js
/公交站/.test('基础设施;交通设施:公交车站')   // → false ❌
```

**「公交车站」里没有连续的「公交站」三个字**（公交-车-站）。
而我的测试用的是**我自己编的**类目字符串（`…:地铁站`），它恰好能匹配。

**教训**：
> **用自己编的数据测自己写的规则，等于没测。**

测试数据必须取自**真实返回**。所以现在：
- 正则改用**词干**（`公交` 而不是 `公交站`）；
- 假地图服务的 POOL 里加了两条**真实事故的复现**数据
  （`基础设施;交通设施:公交车站` / `:地铁站`），并注明"类目字符串取自真实返回，
  不要改成自己编的写法"；
- 新增一条测试专门覆盖真实类目写法的正反例。

**同类教训今天出现多次**：
- 内存仓储比云数据库宽松（本地全绿、线上必挂）
- 假地图服务比真服务宽松（缺 Key 没有修复指引，本地测不到）
- **编造的类目字符串比真实字符串宽松（同一个 bug 犯了两次）**

## 发现：版本校验在生产路径上从未生效（用户发现的前置）

**起因**：用户要求"游玩时标记已到过"。给时间轴加进度按钮时，
顺手补 `trip.progress` 的测试，其中一条断言"传旧版本号必须被拒"——
**它没被拒，反而成功了**。

**排查**：`trip.progress` 写的是

```js
updateCas(TRIPS, id, ctx.expectedVersion == null ? trip.version : ctx.expectedVersion, ...)
```

而前端的调用是

```js
callApi('trip.progress', { tripId, nodeId, status, expectedVersion: v })  // ← 写进 payload
```

但 `utils/api.js` 与后端**都只从信封层读** `expectedVersion`：

```js
callApi(action, payload, options)   // options.expectedVersion → data.expectedVersion
ctx.expectedVersion                 // 来自 event.expectedVersion，不是 event.payload
```

**于是 `ctx.expectedVersion` 永远是 `undefined` → 回落成"当前版本" → CAS 恒成功。**

**后果**：「旧版本确认不得使新方案生效」——**11/5 的验收项，在实际使用中完全没生效**。
而 145 项测试里只有一条覆盖它，那条还是**照着错误的调用约定写的**，所以也是绿的。

**三处都错**（`trip.progress` / `trip.adjust` / `trip.confirmChange`），
**而文档本身就是错的**：参数表把 `expectedVersion` 写在 payload 的花括号里：

```
| trip.confirmChange | {proposalId, candidateId, expectedVersion} | ...
                                            ↑ 读起来就是 payload 字段
```

我是照着文档写的代码。

**修正（三道）**：
1. **文档**：新增 §1.1.1 专讲这件事；参数表把 `expectedVersion` 从 payload 花括号里移出，
   统一写成"＋信封 `expectedVersion`"。
2. **服务端必填**：`trip.progress` / `trip.confirmChange` 缺它直接 `INVALID_PARAM`，
   **删掉"没给就用当前版本"的兜底** —— 那个兜底正是失效的原因。
3. **客户端**：三个调用点改走 `callApi` 的第三个参数。
4. **回归测试**：新增一条，断言"漏传"与"传进 payload"都必须被拒。

**教训**：
> **一个校验如果能被静默跳过，它就不算存在。**
>
> 这个缺陷最坏的地方不是写错了位置，而是**写错位置不报错**——
> 服务端"体贴地"回落成当前版本，于是所有测试都是绿的，
> 而验收项指向的行为从未发生。
> 兜底逻辑要格外小心：它常常正好抵消掉你想要的那个约束。

### 今天最有价值的一段：一类错误的四次修正

## 2026-10-13 深夜 · 内置导航与"地点不入库"

### 内置导航（用户问："不能内置导航吗"）

**能做，数据一样不缺。** 腾讯步行路线接口返回的东西刚好够：

| 字段 | 用途 |
|---|---|
| `polyline` | 真实步行路径 |
| `steps[].instruction` | **中文转向指引原话**（「从起点朝西北行进62米右转进入上游街」） |
| `steps[].polyline_idx` | 每一步对应路径上的哪几个点 |

**唯一的硬障碍是 `polyline` 的差分压缩格式**，现已解开：

```
[lat0, lng0, dLat1, dLng1, ...]
首两个数 = 绝对坐标（GCJ-02）；之后 = 整数增量，单位 1e-6 度
```

**格式是实测确认的，不是猜的**：把 120 个数解出来，末点是
`45.781070, 126.618451` —— **正是这次请求的目的地防洪纪念塔**。
末点落在已知目的地，这不是巧合。另有两条独立佐证：相邻点无跳变、
折线长度与上游声明的 `distance` 吻合。

新增 `trip.legRoute`（某一段的真实路径 + 转向指引）与界面上的内置导航；
**转向指引一律用上游原话** —— 编错一个路口，用户就多走一公里。

「应用内导航」与「微信内置地图」两条路**都留着**：前者不跳出小程序，
后者**有语音**（小程序做不到语音播报，这是平台限制）。

### 地点不再入库（用户决定）

> "以后地点不会入库，全从腾讯地图搜索。"

**问题不是"占空间"，而是**："库里有这条"看起来像"我们确认过这个地方"。
检索回来的是**未核验**的上游数据，和踏勘核验过的混在一个集合里，
准入分级（§5.3）就失去了依据。

现在两条线各归各的，接缝是"对上号"：

```
检索线  place.search  → 候选（不入库）        保证覆盖度
踏勘线  places 集合   → 核验数据（只此一处）   保证可信度
```

#### 一个必须发明的概念：**稳定标识**

检索结果没有数据库 id，但下游处处需要"这个东西是谁"的键。
**必须稳定** —— 否则同一批地点两次规划得到不同的键，
`walkableTo` 永远对不上、**行程无法复现**。

```
placeId（已入库） > poiId（腾讯给的） > 名字 + 千分位坐标（兜底）
```

坐标取**三位小数**（约 100 米）：太精确会被上游坐标抖动搞成两个键，
太粗会把相邻两家店合成一个。

### 一条必须记住的教训：正则做不了 XML 的结构判断

上表最后两条是我自己造成的，而且在"用正则判断 XML 结构"上**错了四次**：

1. 第一版 `wx:else` 规则：把"中间隔着内容"当违规 → 误报 `team-panel` 的合法 block 写法
2. 第二版：分不清"block 内部的内容"与"兄弟元素" → 同一处又误报
3. 第三版：按"最近的兄弟开标签"判定，但不认跨行标签 → 把 `<button>` 当成了兄弟
4. 而那版**错误的转义建议**（"应写成 `&gt;`"）被我照着执行，直接把页面改到编译不过

> **一个会误报的检查比没有检查更糟** —— 它训练人忽略告警，
> 于是连"能抓到一次真问题"的价值也失去。

所以 `test/wxml-guards.test.js` 现在**只留零误报的规则**：
表达式里不得有 `&gt;`/`&lt;` 或原始 `<`/`>`（一律在 JS 里算好布尔量）、标签开闭平衡。
判断不了的情况改成注释里的**人工复核清单**，并写明一条：
**改完点一次「编译」—— WXML 编译失败不会弹错，只会整页白屏。**

**下一步排查顺序（按可能性从高到低）**：

1. **微信开发者工具的"位置"面板**。模拟器默认给一个固定坐标（通常在北京），

3. **坐标系**。全库按 GCJ-02 设计。若某处混进 WGS-84 会有 50–500 米系统性偏移。
   *判据*：偏移量稳定在几百米且方向一致。
4. **`show-location` 原生蓝点**（我这轮从 `false` 改成 `true`）与

### 三、两处解析漏洞（都是用户报的现象，真因都不在现象附近）

#### 漏洞 1：「我想骑车去哈工大」只搜出与哈工大相关的四个地点

用户追问了一句关键的话：**"你在修正则表达式吗，但我连了 api 以后不是 ai 理解吗"**
—— 我第一版只修了规则解析器，而他连了 API，走的是**另一条路**：

    AI 可用（用户连了 API）→ lib/ai/http.js 的**提示词**
    没有模型时            → lib/ai/rulebased.js 的**规则**

提示词的 JSON schema 里**根本没有出行方式这个字段** ——
模型就算听懂了也没地方放。这正是文件里那句：

> **听不懂是模型的问题；听懂了接不住，是 schema 的问题。**

**另一个真因更隐蔽**：「骑车」插在「想」与「去」中间，把 `MUST_STRONG_RES`
的「想去」搅坏了 —— 它抓成「骑车去哈工」（不在库里，被丢弃），
而 `MUST_WEAK_RE` 的「去哈工大」又因值已在 hits 里而跳过：

    输入「我想去哈工大」    → mustVisitTexts = ["哈工大"]   ✓
    输入「我想骑车去哈工大」→ mustVisitTexts = []          ✗

**多两个字就把"必去"降级成了"顺路看看"**，一句话规划于是退化成
"在哈工大附近随便挑几个点"。全程不报错。

#### 漏洞 2：出行方式是"每个目的地"的属性，不是"整句话"的属性

用户："**若多个地名则只自动选择用户说过出行方式的目的地**
（我想骑车去哈工大，再去冰雪大世界 —— 只是去哈工大的方式选为骑车，
**冰雪大世界依旧需要用户自己选择**）"

我第一版把它当成整句话的属性（一个全局 `preferredMode`），
而它会**把"骑车"套到 14 公里外的冰雪大世界上** —— 用户根本没这么说。

### 四、⚠️ 我改判据时差点又走错的一步

用户："我每次搜索完默认帮我选择三个地点，**按理说是一个**"

我第一反应是去调"**什么时候允许**补足"的判据（把 `named.length <= 1`

> **"为什么需要补足，用户说去哪就去哪呗"**

**我是在给一个本来就该删的行为加条件。** 任何补足都是在替他决定要去哪。

原来是 `PACE_LIMITS.normal = 4`，所以"默认三个"其实是候选不足时的结果。

### 五、认地名的规则**收口到一处**

用户："哈工大确实指的是哈尔滨工业大学，**用户输入时会经常输入简写**"
→ 紧接着："那哈工大三个字哈尔滨工业大学七个字**明显不会覆盖一半**"

`matchKnown` 的简称规则是"要覆盖全名一半长度"（3/7 ≈ 0.43 够不到）——
它挡的是"名字里嵌了地标名的民宿"。而中文地名缩写**不是取一半**，
是**取每个词的首字**（哈工大 ← 哈尔滨·工业·大学）。

**我第一版只给一条路加了缩写匹配**，结果：

    输入「我想骑车去哈工大」→ 地点被认出来了（检索词有了）
                            → **必去却是空的**

同一个系统里**两套认地名的规则**，必然出现"一个认、一个不认"。
收口成 `canonicalPlace()`：两条规则按顺序兜，所有认地名的地方都调它。

> **不能靠调小 `matchKnown` 的阈值来兼容缩写**：
> 「哈工大」3/7 ≈ 0.43 与「冰雪大世界 vs 民宿名」5/30 ≈ 0.17
> 在阈值上离得不远，调小到能收前者就会把后者一起收回来。
> **两种规则的形状不同，只能并存，不能合并。**
