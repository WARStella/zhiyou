## 一、这个口径要回答的唯一问题

> **"现有规则在这批样本上的误差是多少？换一个模型能不能更好？"**

在它之前，项目里只有 `ops.walkStats` 的**描述统计**（各距离区间的中位倍率）。
描述统计能说明"估算差多少"，**但不能说明"新方法是否更好"** —— 因为：

| 缺什么 | 后果 |
|---|---|
| 没有基线 | "准确率 92%"不可验证（§6.8.7 第 2 条明确禁止） |
| 没有冻结集 | 调参调到好看，只是在**自己看过的数据上**好看 |
| 两者都没有 | 唯一产出是一段**无法验证的代码** |

## 二、标签口径（**这一节是本节的重点**）

| 量 | 是什么 | 能否当标签 | 理由 |
|---|---|---|---|
| `straightMeters` | 两点的**直线距离** | 特征 | 真实几何量 |
| `actualMeters` | 路径**距离**（名字是历史原因，它**不是**"实际走的距离"） | **标签** | 与直线同为真实几何量，倍率 = 两者相除 |
| `detourRatio` | 路径 ÷ 直线 | **标签**（与上一条等价） | 两端都是真实几何量 |
| `predictedMinutes` | 地图**预测**的耗时 | **特征** | 拿它当标签是**循环论证**：用地图的预测训练模型去预测地图的预测 |
| `actualMinutes` | 用户**真实**用时 | **标签**，但本轮基本为空 | 只能在用户真的走完之后回填（`trip.progress`） |

**三条硬纪律**：

1. **预测与真实必须分开存**（代码里已经分开，测试守住了）。
2. **负标签、零标签宁可不要**：时间倒挂时不标注 —— "一个负的训练标签比少一条样本坏得多"。
3. **首段不标注**：没有可信的起始时刻时，不用计划时间冒充实际时刻。

## 三、评测器做了什么

### 3.1 切分：哈希确定性

```
frozen  ⟸  hash32(seed + _id) % 1000 < ratio*1000
dev     ⟸  其余
```

- **不用随机数**：每次跑得到不同划分，会让"这版比上版好"里混进切分噪声。
- **不按顺序切**：样本按时间写入，取前 N 条会把**同一时段整批**放进同一侧，
  比较就变成"不同场景之间的比较"。
- 同一批数据 + 同一个种子 → **每次同一个冻结集**（有测试守）。

### 3.2 拟合：**只许看开发集**

`fitConstant` / `fitBuckets` 只接受 `split.dev`。冻结集**只在最后打分时出现一次**。

> ⚠️ 泄漏的表现不是报错，而是**分数变好**。所以测试断言的是
> "**把冻结集标签改成离谱值，拟合出的系数必须一模一样**" ——
> 只断言"分数在动"是抓不住泄漏的。

### 3.3 打分：中位数，且带符号

| 指标 | 定义 | 为什么 |
|---|---|---|
| `mapePercent` | **中位数**绝对百分比误差 | 一条上游异常值能把均值拉走；"中位差 12%"能拿去答辩，"均值差 340%"不能 |
| `biasPercent` | **带符号**的中位相对误差 | 只说"差多少"不够；"系统一贯高估 20%"才能指导修改 |

### 3.4 判决：三个出口必须分得开

| 出口 | 含义 |
|---|---|
| `null`（真的打败了） | 更准，**且**相对改进 ≥ 阈值 |
| `NOT_BETTER` | 更差或持平 |
| `GAIN_BELOW_THRESHOLD` | 确实更准，但好得不够（可能来自切分噪声） |

**"没打败基线"与"样本不够，无法判断"是两句不同的话**，不合并。

## 四、门与阈值（**必须冻结**）

| 参数 | 值 | 性质 |
|---|---|---|
| `MIN_SCORE_SAMPLES` | 30 | "能号称跑过一次评测"的最低限度，**不是功效分析结论** |
| `MIN_BUCKET_SAMPLES` | 5 | 沿用 `ops.walkStats` 的口径：不足就不给系数 |
| `MIN_RELATIVE_GAIN` | 5% | **人为设定**，用于防止"改进 0.3% 就宣称胜利"；正式实测前冻结（§11.4） |
| `PRODUCT_CONSTANT` | 1.3 | 产品现状（对照基线之一） |

> 低于 30 条时**分数一律为 null**，"不给一个看起来很精确的小数"。

## 五、怎么跑

```powershell
# ① 导出（仅 dev；返回体有大小上限，注意 truncated）
#    云函数控制台调用 ops.exportWalkSamples  { limit: 1000 } → 存成 json

# ② 评测
node scripts/walk-eval.js --samples <导出的 json>
node scripts/walk-eval.js --samples <json> --ratio 0.3 --seed zy-walk-2026
node scripts/walk-eval.js --samples <json> --json      # 归档用

# ③ 只想验证评测器本身能跑（**合成数据，不是实测**）
node scripts/walk-eval.js --demo
```

- **退出码恒为 0**：这是报告不是测试。样本不足是**结论**，不是失败 ——
  用退出码报失败会诱使人为了"让 CI 变绿"去砍阈值。
- 不给 `--samples` 也不给 `--demo` 时，明确打印"**没有评分**"，不用合成数据顶替。

## 六、当前能评什么（2026-10-15 的诚实状态）

| 目标 | 可评性 | 说明 |
|---|---|---|
| **距离倍率**（直线 → 路径） | ✅ **可评** | 每次真实调地图接口自动记一条，**不需要任何人走路** —— 这是范围收缩后（计划书 v7.1 §1.3）**唯一还能持续增长的定量数据** |
| **真实用时**（`actualMinutes`） | ❌ 本轮不可评 | 需要真人真走。评测器**只报覆盖率，不给分数** —— 给它编一个分数，等于用"没有数据"产出"看起来有数据" |

## 七、下一步（**有门，不是流程**）

1. 攒样本（自动进行）：每次真实规划都会记，无需人工干预。
2. 冻结测试集：样本量到 200–500 条时，冻结一次划分与阈值，**之后不再改**。
3. 训练候选：结构化特征 + 线性／小 MLP（**不需要 torch**，numpy 足够），导出小参数表（§6.8.2 形态①）。
4. **过门才继续**：候选必须打败"分段常数"基线且超过阈值。
   - 过不了 → **停在这里就是结论**："在该样本量下规则已足够"。
   - 这是 §6.8.5 明确写下的、**可接受且大概率**的结果。

> **交付物不是"我们用了某个模型"，而是"我们证明了它在什么条件下比规则好"。**
> 后者才是 AI 维度真正认可的东西（§6.8.8）。

## 八、明确不做（避免下一次又从头讨论）

| 不做 | 为什么 |
|---|---|
| **位置纠偏**（CNN-1D / 时空 3D 卷积） | 需要**历史轨迹**，而轨迹来自真实出行 → 无外场即无数据（§1.3） |
| **地图瓦片可达性**（CNN-2D / FCN） | 需人工标注瓦片，成本本届无法承担 |
| **集合点排序**（GNN）、**停留时长**（RNN） | 需要"哪次集合成功了""行程真的走完了"的标注 → 同上 |
| 用模型替换已跑通的规则 | §6.8.7 第 1 条：规则是**已经拿到的分数**，模型只做**增量** |

**关于 CNN-3D**：把「时间 × 经纬度」栅格化成体素做三维卷积，
在问题定义上属于**位置纠偏**的一种网络形状（与 CNN-1D 解决同一件事，只是把空间也做成卷积维度）。
它同样依赖历史轨迹 → **本轮不做**；若日后恢复外场实测并攒到轨迹，它是该问题的**首选候选**。
