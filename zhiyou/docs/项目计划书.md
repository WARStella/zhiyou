## 一、项目目标与用户价值

智游·灵动是一款微信小程序，为城市游览中的个人和同行小队提供行程调整、位置协同与集合接续。个人规划提供基础能力；小队共同路线、现场变化后的调整、集合后接回行程构成主要使用流程。

主要入口为【行程】【队伍】【我的】。用户可以用文字或语音提出需求，在真实地点候选中确认位置；系统检查时间与步行约束，展示方案及依据，用户确认后才改变行程或发起集合。

统一随行游览助手首版已实现文字/语音/照片入口、受限工具编排、真实 POI 候选确认、有来源资料检索和集合选点接续。代码与本地验证不代表已部署；真实模型、照片识别与微信真机流程仍待验证。具体边界见第五章。

## 三、核心功能与使用流程

### 3.1 个人规划与连续修改

文字/语音需求 → 需求理解与必要追问 → 检索并确认具体 POI → 路线和约束检查 → 展示候选 → 用户确认。未确认提案不得改变原行程，确认后从新版本继续；历史到达、已完成节点与实际时间保留。模型不可用时显示规则降级，无法满足硬约束时明确说明冲突。

### 3.2 小队协作与集合

在【我的】建队/入队；每人主动同意后开启位置共享；在【队伍】查看有效位置、聊天、推荐或手动选择集合点，设置未来集合时间，再发起、确认、到达和检查出发。计划集合、实际到齐和实际出发分别记录。

自动集合推荐使用成员平均位置，取中心周围 1 公里内最近地点，无结果回落到中心；成员步行估算与真实路网结果分别标明，不把直线距离冒充可达性证明。

### 3.3 地图与文字/语音聊天

成员标记采用当前资料头像，无头像时有默认显示；文字只保留用户名。消息作为姓名上方独立蓝色气泡短暂出现，姓名维持原色白底，最多约 8 秒后清除；过期位置用半透明头像区分。坐标消息按服务端稳定成员键关联，重名、同坐标不串人，切队/撤权/隐藏按既有逻辑清理。

常用交流在地图下方的同一输入框完成：点击文字区打字、框内话筒实时识别，编辑后手动发送；没有二级聊天入口。左下预览保留最近两条，消息记录不会因坐标提示消失而自动删除。

### 3.4 OCR 辅助集合选点

拍照/选图 → 本地预览 → 主动点击识别 → 核对并编辑名称 → 搜索所提供位置周围 3 公里内真实 POI → 查看地址和位置 → 确认本地集合点 → 设置时间并主动发起集合。图片识别不自动建立集合任务，进行中的任务不被覆盖；无可靠结果可手动输入或地图选点。

## 四、系统架构与业务边界

- 前端为微信小程序；统一业务云函数为 api，定时清理由 timer-cleanup 执行。客户端不直写业务库，云端每次验证身份与队伍权限。
- 数据存储为微信云数据库，仓储层支持云端与测试内存实现。当前注册 17 个集合，新增 `guide_sessions`，以代码登记表及第五章追加结构为准；早期“14 个集合”是当时快照。
- 腾讯位置服务承担 POI/路线相关能力，高德承担现有公交地铁/地点照片能力；各自 Key 留在云端。路线来源、预测与实测分开显示。
- 腾讯云 ASR 已接实时语音转文字；腾讯云 OCR 新增照片文字识别。不同服务的配置、权限、额度与计费分别核对。
- 提案确认、版本校验、幂等和事务用于保护行程与队伍写入。语音签名、未提交识别结果及须实时鉴权的聊天/OCR/游览会话查询不进入通用响应缓存。
- 位置共享须主动同意且可撤回。密钥、签名 URL、原始录音和照片不能因调试写入客户端源码、业务事件或文档；保留策略见数据模型和专项章节。

## 五、统一随行游览助手 Agent

### 5.1 产品目标与状态

2026-10-17 用户确认优先实现统一助手，并记录0.2.0加入此功能。当前代码提供一个【随行游览助手】页面，从【行程】或【队伍】的可拖拽悬浮气泡进入，原卡片入口移除。最新松手打开修复后，用户已反馈拖动、点击测试通过，助手真实业务全流程仍需分别验收。气泡默认位于右下方，拖动时限制在窗口范围内，松手吸附左右边缘；单指短按未拖动时松手直接打开助手，兼容没有后续 tap 回调的情况。抬手后的 tap 与快速重复点击不误开多个页面，长按/拖动/取消不进入。助手页面支持文字提问、语音转文字后手动提交、拍照/选图后主动识别。加入队伍不是只读讲解的前提；准备集合点需要当前有效队伍身份。

入口由两页共用的 `components/guide-entry` 实现，用普通固定定位 view 渲染，图标/文字的指针统一交由根节点处理，只有气泡自身捕获触摸，未设置拦截整屏的拖动层。手势兼容三组坐标字段、缺失结束坐标或 identifier；真实 tap 可完成遗漏 touchend 的未移动手势，拖动与取消仍阻止误跳转。以本地 `zhiyou-guide-entry-position` 保存左右边缘和高度比例（界面位置，不是地理位置），两页切换恢复，窗口尺寸改变重新计算边界。多指/触摸取消/隐藏时取消当前手势；软键盘弹出暂时隐藏气泡，关闭后恢复，组件销毁解除键盘监听。页面底部增加留白，让最后一项可滚出悬浮遮挡区域。入口修复重新编译并更新小程序即可；队伍地图同层显示、地图操作与拖动手感仍待真机验收。

首版流程：拍照问“这是哪里，有什么历史，能在这集合吗？”→ 视觉模型提取线索，失败/未配置回退 OCR → 文本模型选择真实 POI 搜索 → 人工核对名称、地址和位置 → 确认后继续资料检索与集合建议 → 点击“用作集合点”二次确认并回到队伍页 → 设置未来时间并手动发起。助手不会调用 `meet.create`，也不会修改行程。文字地名使用同一确认流程；模型不可用会明确显示受限规则降级。

### 5.3 验收边界

- 根据问题实际选择工具并处理歧义；固定“拍照后输出一段文字”不直接计作完整 Agent。
- 图片与检索材料中的文字按资料处理，不能成为越权执行指令。没有可靠地点证据时不能编造坐标或强行匹配景点。
- 先确认地点，再共享该地点上下文进行讲解和后续操作；支持纠正与放弃，不把别处资料混为当前景点。
- 景点讲解展示来源、发布日期（有则显示）、资料核对日期；票价、营业时间等动态事实尚无实时来源，明确拒绝推测并提示查官方渠道。
- 修改行程和发起集合前继续检查用户权限、输入参数及版本，并由用户确认。无检索结果或服务失败时明确说明，保留手动路线。

### 5.4 编排、接口与会话数据

云端 `lib/guide/agent.js` 每轮读取问题、已确认地点、图片线索、最近对话与工具观测；文本模型返回受限 JSON 工具选择，执行后再次决策。允许搜索、检索、集合建议、行程状态、集合状态、修改提案、结束七种选择，最多3轮工具步骤，45秒步骤间预算；单次文本请求8秒、识图20秒，不执行任意工具、URL 或代码。提示词版本 `guide-agent-v3`，资料版本 `harbin-guide-20261017-v1`。明确的状态/修改意图受服务端规则约束，模型不能把只读问题改成修改；读取对象来自请求所选行程及队伍 activeTripId，不采用模型给的行程ID。图片路径不生成行程修改提案。导航、YOLO 计数是用户主动操作的独立接口，不假称所有步骤均由模型决定。

2026-10-17 按用户最新选择，识图、工具选择和资料片段选择默认统一请求 DeepSeek 官方 `https://api.deepseek.com/chat/completions`，模型固定 `deepseek-flash`，图片以 base64 data URL 在 user 消息中发送、detail 为 high。显式关闭思考（`thinking.type=disabled`），使用 JSON object、非流式输出，输出上限900 tokens；上游报错或输出被截断不记为识别成功，继续既有回退。采用官方当前支持图像输入的 Flash 模型，不能把旧 `deepseek-chat` 或不支持图片的 Pro 当作视觉模型。

| action | 输入 | 输出 | 权限与语义 |
|---|---|---|---|
| `guide.ask` | `{text?,imageBase64?,center?,crewId?,tripId?,scope?:trip/team,sessionId?,candidateId?}`；续问在统一信封带 `expectedVersion` | 原会话字段及按需返回的 `tripContext / meetingContext / tripChange / tripPlan` | 登录；行程本人或有效队员可读，团队修改仅发起人；1,000字、JPG/PNG≤1MB；候选确认不夹带新文字/照片。会话及业务读取版本在提交事务内复核；每用户近一分钟已记录请求达到6次则限频，不承诺严格并发配额 |
| `guide.get` | `{sessionId,crewId?}` | 同会话视图 | 仅本人，队伍范围须匹配且仍有效，过期拒绝；用于冲突刷新，不自动重试昂贵调用 |
| `guide.close` | `{sessionId}` | `{closed:true}` | 仅本人清除，也允许本人离队后删除；不返回旧对话 |
| `guide.navigation` | `{target:next/meeting/place,crewId?,tripId?,scope?:trip/team,sessionId?}` | `{point,name,address,target,serverTime}` | 当前已授权行程、未结束集合或本人会话中已确认地点；不采用传入的任意坐标；不写业务、不缓存结果 |
| `guide.countPeople` | `{imageBase64}`，JPG/PNG≤1MB | `{count,boxes,model,estimated,confidenceThreshold,truncated,notice}` | 登录后主动检测；无服务明确报未配置，不用语言模型猜人数；每用户近一分钟记录达到6次限频；不存图片/结果、不进入通用缓存 |

第17个集合 **`guide_sessions`** 仅管理端读写，客户端只能经上述 API 访问。字段：`_id/ownerId/crewId/version/place/candidates/clues/pendingQuestion/messages/lastResponse/expiresAt`。最近对话最多8条；保存用户主动提交的问题、图片是否存在的标记、地名线索、已确认地点坐标、来源和回答，不存照片或 base64。闲置30分钟后 API 拒绝读取；实际删除由每小时清理任务完成，过期到物理删除之间可能等待下一次定时运行。可建 `expiresAt` 升序非唯一索引用于清理，不能把普通索引当作 TTL。

本轮 `lastResponse` 可含当前行程/集合版本及查询快照、修改提案/追问摘要、已确认目的地的首次规划草稿；内部事务校验信息不返回、不写会话。YOLO计数和导航不写入会话，也不新增业务集合。

以上五个助手接口跳过通用 `operations` 响应缓存；事件只记录调用状态，不复制正文/照片。每轮事务防并发覆盖及清除后复活，状态读取还检查行程版本与集合 revision。页面清除会话会尝试远端删除；初次请求尚未拿到会话ID就关闭页面的记录依靠过期清理。隐藏/切队/切换当前行程/销毁作废迟到回填；相册/相机选择过程中临时隐藏只保留选图回调，不自动上传。图库原临时文件由微信管理，压缩副本读完尝试删除。已发送的第三方请求不能承诺取消用量或第三方零保留。

助手从行程页进入使用 `zhiyou-active-trip.tripId`；没有选择时可回落到当前队伍共同路线。从队伍入口带 `scope=team`，只读队伍 activeTripId，避免误用个人路线。查询时刻与版本展示为快照，再次提问才重新查询。下一站为 seq 最前的 pending，已到达站单独显示；全部完成或跳过不回到第一站。集合终态（取消/出发/完成）不继续倒计时，参与者仅统计当前版本有效确认，不展示他人身份或位置。

修改的提案/追问由既有 `trip.adjustText` 生成，固定 `autoApply=never`；不确定地点、分钟或结束时刻须补充。助手内选择可行方案并二次确认后调用 `trip.confirmChange`，保留版本检查、发起人权限和历史节点；网络失败可用同一请求号重试确认。隐藏/切换上下文前未完成的确认不发送。确认成功后行程页再次显示时读取刷新标记，重新拉取新版本；保持页面切换不丢已确认修改。

无当前有效路线时，明确单目的地请求由服务端按真实地名检索，不依赖模型决定是否进入首次规划。候选确认后返回 `tripPlan:{destination:{name,address,point},stayMin:60}`，尚不写行程。用户选择当前位置或地图出发点、停留分钟、方式；弹窗明确现在出发、生成个人行程，复用 `trip.plan`，不自动发布队伍路线。网络重试保持同请求号/出发时间，创建成功但打开失败只重开已有行程。`zhiyou-guide-created-trip` 仅交接ID/版本，行程页通过 `trip.get` 重新鉴权读取，成功消费交接并更新当前行程；读取失败可再进入重试，隐藏后的旧结果不覆盖页面。否定、询问与复杂多目的地文字不默认为单站初次规划。

2026-10-17 云端写入修复：事务适配器对普通对象/数组字段用数据库 `command.set` 整体替换，避免初始 `lastResponse/place: null` 被 SDK 展开为子路径导致失败，也避免旧结果残留。历史 null 文档直接兼容。遇到 `Cannot create field 'answer' in element {lastResponse: null}`，需上传部署最新完整 `api`；本次修复不需要重新初始化数据库或更改环境变量。详见[开发日志](开发日志.md#guide-null-write-fix)。

### 5.6 导航与照片人群计数的使用

行程页内置导航修复：点“到了”或更新完成/跳过进度时，当前目标选首个pending，旧路线与转向指引立即作废；之前已开启导航时，返回行程页重新定位并查询下一站，全部到达/完成/跳过则退出。跨过跳过站点不沿用原相邻段数据。前端按行程ID、版本、目标与请求代次拒绝迟到响应，停止/隐藏/重设后旧导航不复活；后端地图请求前后检查版本。此更新依赖用户标记进度，没有新增GPS自动判定到达。

在助手点击“导航到下一站”“导航到集合点”，或确认景点后点击“导航到已确认地点”。服务端每次重新查询权限与目的地；下一站仅选 pending，集合取消/出发/结束不继续导航，未人工确认的地图候选不能直接用于该入口。返回有效坐标后调用微信内置地图 `wx.openLocation`，用户在地图内选择路线与开始导航。此项不增加应用内语音播报、持续后台定位或离线导航；行程页原有真实步行路线/分步指引继续保留。

拍照/选图后点击“YOLO 人群计数”，或输入“照片里有多少人”后提问，走专用 YOLO 计数接口。只有这两种主动操作才上传计数；一般地标识别仍走 DeepSeek/OCR。计数结果单独显示约多少人和检测框，包含模型、阈值、数量上限提示；零人也正常显示。使用预训练 YOLO11n 的 person 类，不识别身份、不做跨照片去重，不按检测数推断现场安全容量、拥挤等级或实时人数。遮挡、远处小目标、照片边缘可能漏检或误检；密集人群评测与专用模型仍属后续工作。

推理代码为 `services/crowd/app.py`，FastAPI＋Ultralytics，单CPU模型串行推理，忙时返回429；固定 `classes=[0]`、`conf=0.35`（可由服务环境调整）、`iou=0.45`、960输入、最多1000框。不把原图、base64或检测结果写入数据库/磁盘，只有本地预览暂时保留照片路径和框；清除/离开后沿用页面生命周期处理。模型与数据处理依据[官方预测接口](https://docs.ultralytics.com/modes/predict)、[YOLO11模型说明](https://docs.ultralytics.com/models/yolo11)及[线程安全建议](https://docs.ultralytics.com/guides/yolo-thread-safe-inference)；依赖和权重许可按对应官方发布执行。

### 6.1 队伍邀请分享与小程序码（2026-10-17实现）

入口为「我的 → 小队 → 邀请同伴/小程序码」；未加入小队时可点「扫码查看入队邀请」。发起人创建有效期7天的邀请，可发送微信邀请卡、生成小程序码并保存相册。已入队成员可以分享当前有效邀请，创建、更新、撤销仅限发起人。更新使旧卡片和旧码失效，撤销不影响已有成员；原六位邀请码仍可使用，不属于此邀请令牌的撤销范围。

接收方从卡片、微信扫描或应用内扫码打开独立邀请页，自动取得微信身份后仅预览队名、人数、有效期和本人是否已加入；点确认后才入队并切换至队伍页。不会自动共享位置，不返回成员名单、坐标或六位邀请码。邀请到期、撤销、更新、队伍解散或发起人失去成员资格均不能加入；确认加入时在队伍事务内重新核验，不依赖旧预览。重复确认不重复增加人数，跳转失败可重新打开队伍。

邀请字段放在现有 `crews`：`invitationToken`（18字节随机值编码为24字符）、`invitationStatus`、`invitationCreatedBy`、`invitationCreatedAt`、`invitationExpiresAt`，每队一份当前邀请，不新增集合。小程序码scene为 `i` 加令牌共25字符，固定落地页 `pages/invite/index`。邀请接口不进入通用响应缓存，每次核验当前身份；事件只记录接口结果，不保存令牌、码图片或预览成员信息。生成前检查最近一分钟调用记录，达到6条后拒绝继续生成；并发情况下该检查不是严格分布式限流。生成期间撤销或离队会在返回前再次拒绝。码图写入客户端临时文件，重新生成、失效或离开页面时清理；不会上传至云存储。

统一部署时上传 `api`（含 `config.json` 的 `wxacode.getUnlimited` 云调用权限）和新小程序页面，无需新AppSecret。可选环境变量 `WX_CODE_ENV_VERSION=trial` 用于体验版码；`release` 用于正式版、`develop` 用于开发版。未填写时生产环境默认release，其余默认trial；对应版本须包含邀请页，正式版码开启页面路径检查。微信真实生成、体验/正式版扫码、邀请卡转发和相册权限在最终统一真机验收中验证；当前本地测试不代表微信已生成或投放成功。

已实现的边界（代码现状，**不等于已送达**）：发送走 `cloud.openapi.subscribeMessage.send` 云调用，AppSecret 与令牌不经过客户端；`api/config.json` 已登记 `subscribeMessage.send` 权限。意向由 `subscribe.report` 记录，只有 `accept` 记为同意，`reject/ban/filter` 与未知值一律算未同意；重复点击累加次数而不重置。收件人只取当前 `status=active` 成员并排除本人，离队/被移除/解散后不再推送。同一业务事件用唯一键 `notice_log.dedupeKey` 抢占（唯一索引），抢不到直接跳过 —— 聊天自身重试不会变成重复通知；消息类通知按 60 秒时间窗合并，连发多条只花一次授权。微信返回 43101（未订阅/次数用尽）时把该意向标记 `revoked` 并保留历史计数；云调用抛异常属"未知结果"，记为 `unknown` 且**不自动重试**，避免同一句话发两条。**通知失败一律不影响已落库的聊天、集合与确认结果**（单人发送异常被隔离，不会让后面的人收不到）。

点击通知的落地按交接文档第 3 节第 7 条实现为"**先鉴权、再恢复上下文**"：落地页只带 `crewId`/`meetId` 这类定位线索、不带消息正文；页面先调 `crew.get` 对目标队伍重新鉴权，**通过后**才把 `zhiyou-active-crew` 改写为目标队伍并按其重新拉取成员、集合与消息（tab 页不能带 URL 参数，沿用 storage 交接）。鉴权失败（已退出/被移除/已解散）时**不改写活动队伍**，显示"这条提醒所属的队伍已不可访问"并给出「去切换队伍」入口。集合通知落地后再核对那场集合是否仍在进行，已结束/已取消就如实说明，不假装定位到集合。冷启动路径下页面 `onShow` 未必拿到 query，因此 `App.onShow/onLaunch` 会把落地参数抄入 `zhiyou-notice-landing` 作为兜底，页面**读完即清**且 2 分钟过期，避免用户下次自己打开时又被带回旧提醒。

已读缺口同时补上：`chat.markRead` 把本人已读游标持久化到 `crew_members.chatLastReadSeq`，只增不减且不超过队伍 `chatSeq`。地图页在**消息真的渲染出来之后**才推进（`map-chat-preview` 回报 `chatPreviewLatestSeq`）；拉取接口、地图预取、推送成功都不自动等于已读。已读者不再被提醒，避免把授权次数花在已经看到消息的人身上。

仍需处理或真机验证：部署 `api`（云端安装依赖、同步 `permissions.openapi`）后确认三个模板已在小程序后台启用；两名成员真机互发消息并建一次集合，核对关闭小程序后的送达、点击落地、已读后不再提醒。普通一次性订阅须用户主动授权、按次数消耗，不能承诺一次开启后持续接收所有聊天；用户后台长期订阅为空，不视为已经取得长期资格。长期规范只维护本计划书和开发日志。

用户另询问入队是否统一行程。已核对：`crew.join`/`crew.inviteJoin`只变更成员与计数，不改任何个人路线；`team.publishTrip`仅允许发起人将自己的个人路线复制为独立共同路线，其他成员有权读取该路线，但自己的个人路线保留。当前小程序尚未完整提供可见的共同路线发布/查看入口（仅留后端接口和旧组件方法），属于后续功能补齐项，不能把后端已有等同于页面可用或入队自动统一行程。

### 7.1 环境与配置

在当前小程序使用的云开发环境中部署 api 与已有清理函数；选择正确环境，保留原有变量并按服务增加配置，不把本地进程环境与云函数环境混同。

| 服务 | 配置入口与必要信息 | 说明 |
|---|---|---|
| 地图 | api 环境变量 MAP_KEY | 腾讯位置服务 WebService Key |
| 公交地铁/照片 | AMAP_KEY，及已有 MAP_PROVIDER/PHOTO_PROVIDER 等选项 | 高德 Web 服务，按项目已有适配配置 |
| 文本 AI | AI_API_KEY 及现有模型/地址配置 | 按实际 provider 能力使用；视觉能力需另核 |
| 游览助手（默认 DeepSeek，识图与对话统一） | `GUIDE_PROVIDER=deepseek`（留空也默认此值）；使用 `GUIDE_DEEPSEEK_API_KEY`，未填则复用 `AI_API_KEY`，必须为 DeepSeek 官方 Key | 固定官方地址和 `deepseek-flash`；单个 Key 即可支持识图、工具选择和资料片段选择。默认模式不读取旧 `GUIDE_AI_* / GUIDE_VISION_*` 或全局模型/地址覆盖，避免继续请求智谱或使用旧模型 |
| 其他兼容服务（保留显式选择） | 只有 `GUIDE_PROVIDER=compatible` 才读取原有 `GUIDE_AI_* / AI_*` 文本配置与独立 `GUIDE_VISION_API_KEY / GUIDE_VISION_BASE_URL / GUIDE_VISION_MODEL` 视觉配置 | 本轮用户选择 DeepSeek，此模式无需开启；仍要求 HTTPS、data URL 与 JSON object 输出，地址不带 `/chat/completions` |
| YOLO 人群计数 | api 云函数配置 `YOLO_BASE_URL`、`YOLO_API_KEY`；独立服务配置同一 `YOLO_API_KEY` | 地址为部署后的HTTPS根路径，不带 `/count`；Key不进入小程序。模型默认 `yolo11n.pt`，CPU检测，不依赖DeepSeek Key；完整部署见 §7.4 |

| OCR | OCR_SECRET_ID、OCR_SECRET_KEY；使用临时凭据时另填 OCR_SESSION_TOKEN | api 云函数→配置→环境变量，值为同一对 SecretId/SecretKey；不是微信 AppID，也不新增数字 APPID |

OCR 启用须确认 GeneralBasicOCR 可调用，子账号核对 ocr:GeneralBasicOCR 权限。API 密钥留云端，值不加额外引号或空格；已有密钥有权限时可显式复用，不自动借用 ASR 变量。保存配置后上传部署最新 api 并重新编译/更新体验版。OCR 请求从云端发出，无需为 OCR 新增小程序 request/socket 域名。

**助手部署步骤：** ①上传部署最新 `api`，将云函数超时改为60秒（旧接口章节20秒是原功能配置，新助手串行工具需要更长预算）；②管理员执行 `ops.initDb({confirm:true})` 建立新增的 `guide_sessions`，确认仅管理端读写，按返回清单建索引（含会话 `expiresAt` 升序、事件 `action + userId + type + ts(desc)` 非唯一组合索引，后者用于助手限频查询）；③重新部署 `timer-cleanup` 并保留每小时触发器，增加会话过期清理；④保留原地图/ASR 配置，默认助手设 `GUIDE_PROVIDER=deepseek`，确认 `AI_API_KEY` 是 DeepSeek 官方 Key，或单独填 `GUIDE_DEEPSEEK_API_KEY`；OCR 为识图失败回退，按需沿用；⑤更新小程序体验版及实际隐私用途。`ops.health` 的 `deps.guideService` 展示 `modelProvider / textModel / visionModel / configured / visionConfigured` 和知识版本；DeepSeek 模式应为 `deepseek / deepseek-flash / deepseek-flash`，两项 configured 在有 Key 时为 true；这里只检查配置，不证明网络、余额、权限或识别成功。

模型请求均从云函数发出，无需为助手新增小程序模型 request 域名或插件。语音仍沿用腾讯 ASR socket 域名。隐私指引须按实际配置说明默认照片、提问与资料片段会发送至 DeepSeek，识图失败启用回退时照片会发送至腾讯 OCR，私有会话短期保存文字与确认坐标。新增能力不替代既有内容安全待办。

### 7.4 本轮新增能力的部署步骤

状态问答、修改提案和地图导航需**重新部署完整 `cloudfunctions/api` 并更新小程序**。沿用既有 DeepSeek/地图配置、60秒云函数超时和会话清理，无新增集合；本轮两个新接口不需要重建业务数据。修改解析沿用原 `trip.adjustText` 的 AI 配置，未配置模型则明确规则降级。YOLO 是单独的 Python CPU 服务，不能把 PyTorch 权重直接塞进现有 Node.js api 云函数。

1. 在可运行 Docker 的机器/容器平台上，从项目根目录构建：`docker build -t zhiyou-crowd services/crowd`。构建会安装CPU依赖、下载官方 `yolo11n.pt`；需要能访问 PyPI、PyTorch 和官方权重地址。本地Windows CPU已验证，Docker镜像构建及用户云主机未在本轮实测。

   Git部署当前仓库 `Shangjie-Li2002/zhiyou-yolo` 的文件位于 `zhiyou-yolo-deploy/`：目标目录填 `zhiyou-yolo-deploy`，Dockerfile名称 `Dockerfile`，端口8000。更新入口已由用户截图确认：服务详情→服务配置→右上角“更新服务”。001在CPU包下载后哈希失败；002使用重试版仍失败，日志止于下载开始，没有具体终止原因。最新Dockerfile固定pip26.2.1及torch2.14.1+cpu/torchvision0.29.1+cpu，改为南京大学镜像的两个固定wheel URL，URL中钉住官方SHA-256，通用依赖仍走PyPI。连接超时60秒，连接/续传重试各3次，CPU安装最多3轮，升级pip后开启raw下载进度；业务依赖继续约束CPU版本并执行 `pip check`。本机完整下载两个镜像文件的哈希均与官方匹配，总约34秒；这不等于云端出口验证。以上001/002为排障历史；后续003更新服务后已获得健康就绪与空白图计数证据，见本节第6步。
2. 在部署机器准备受控的 `crowd.env`，只写 `YOLO_API_KEY=你生成的随机服务密钥`；密钥建议为至少32位随机串。该文件不放入小程序、源码提交或公开截图。Docker已默认CPU模型和阈值，也可加 `YOLO_CONFIDENCE=0.35`。
3. 自管机器示例：`docker run -d --name zhiyou-crowd --env-file crowd.env -p 127.0.0.1:8000:8000 zhiyou-crowd`。模型加载后服务就绪。容器平台按其规则暴露8000端口；不要同时照搬自管机的回环绑定。
4. 给服务配置真实的HTTPS域名/入口（443）。自管机可由Caddy/Nginx将该HTTPS域名反向代理至 `127.0.0.1:8000`。`GET /health` 和 `POST /count` 均需 `Authorization: Bearer 同一密钥`；入口请求体上限应允许约1.4MB JSON，服务会再检查JPEG/PNG≤1MB与≤1600万像素。
5. 在 `api` 云函数环境变量填 `YOLO_BASE_URL=https://你的实际服务域名`（不带 `/count`）和 `YOLO_API_KEY=同一密钥`。重新部署api。`ops.health.deps.crowdService.configured=true`只证明配置格式就绪；还须调用真实计数验证网络、鉴权和推理。该服务由云函数调用，小程序不新增YOLO request域名。
6. 重新编译、预览或更新体验版。先验证“下一站去哪”“距离集合还有多久”；再验证“下一站少待十分钟”生成提案但不改变行程、确认后刷新；分别测试下一站/集合点/已确认景点导航。最后上传可人工计数的人群照片，核对框、计数、零人、拒识和服务未配置/失败情况。

   2026-10-17后续003部署已取得云端实证：用户反馈配置成功，实际HTTPS健康接口无密钥401、有密钥200并返回ready=true；合成320×320白色PNG的/count为200、0人/0框，约1.73秒。没有用户照片或小程序调用参与该测试，不替代真实人群和完整页面验收；Node api环境变量仍须与服务保持同一密钥及根地址。

若暂不部署YOLO，状态问答、修改及导航仍可使用，点击计数会明确提示未部署；不会改用大模型编造检测人数。照片计数用途和实际推理服务处理方应同步写入隐私指引；应用及当前服务代码不主动保存上传原图，云平台和反向代理日志须按实际部署核对。

8. YOLO：真实人群照片与人工计数对照，记录漏检/误检、零人、遮挡与小目标；检测框随本地原图比例显示。验证鉴权、1MB/像素上限、忙时拒绝、上游超时、切页无迟到回填，不将两张本地冒烟图当作真实人群准确率。
9. 首次规划与行程页导航：无当前行程时说“想去哈尔滨学院”，先核对候选，再设置出发点、停留及方式；取消不创建，确认后显示真实生成的个人行程。定位拒绝可手动选点，创建/跳转失败不重复创建。行程页开启导航后标记到了，返回时目标、折线和指引均变为下一站；最后一站无旧导航，跳过中间站不使用旧段耗时；退出/隐藏期间旧请求不回填。

### 0. 三个必须先定死的结构性决定

文档型数据库没有外键，所以"数据关系清楚"不能靠数据库强制，只能靠**三条纪律**。这三条今天定，后面 5 周都不要再讨论。

#### 决定 1｜小程序端不直连数据库，只有 `places` 例外

| 访问方 | 权限 |
|---|---|
| 小程序端直连数据库 | **仅** `places` 可读（`{"read": true, "write": false}`） |
| 小程序端直连其余集合 | **全部关闭**（`{"read": false, "write": false}`） |
| 云函数 | admin 身份，是**唯一写入口** |

**理由**：云函数用 admin 身份访问数据库，会**绕过**安全规则。所以"非成员无法读取队伍位置"这条验收，**不可能靠数据库安全规则实现，必须在云函数里显式校验**。权限只有一处实现，才可能测。

代价是所有读都走云函数。可接受：`places` 才 8–12 条且几乎不变，放开直读是为了少一次冷启动。

#### 决定 2｜所有写操作带版本号，用条件更新做 CAS

团队行程和集合任务都是并发场景（两人同时确认、旧卡片回放）。做法统一为：

```js
// 伪代码：只有版本号还对得上，才允许写入
const r = await db.collection('trips')
  .where({ _id: tripId, version: expectedVersion })   // ← 乐观锁
  .update({ data: { ...patch, version: _.inc(1) } })
if (r.stats.updated === 0) throw new AppError('VERSION_CONFLICT')
```

`updated === 0` 说明版本已被别人推进 → 返回 `VERSION_CONFLICT`，**不写入**。这一条机制同时兑现三处验收：
- 10/24「旧版本确认不能使新方案生效」
- 10/25「打开旧卡片不会执行旧方案」
- 11/11「并发确认」异常测试

#### 决定 3｜位置来源可替换，算法不感知来源

`locations.source` 取 `gps | manual | poi | fuzzy`。**集合推荐算法只吃 `{point, reportedAt, accuracyM, source}`**，不关心坐标是怎么来的。

**为什么这是今天最重要的设计**：`wx.getLocation` 属于[地理位置准入接口](https://developers.weixin.qq.com/doc/oplatform/Third-party_Platforms/2.0/product/apply_privacy_api.html)，权限未批时不仅调用失败，代码连审核都提交不了。降级路径是**用户在地图组件上手动选点**（`map` 的 `bindtap` / `MapContext.getCenterLocation`），这条路不调用受限接口。若把"位置"写死成 GPS 语义，降级就要重写集合推荐与集合任务两个模块；留一个 `source` 字段，降级只是客户端换一个入口。

界面必须显示来源与时效（§8.2），所以 `source` 和 `reportedAt` 本来就要回传，不是为降级额外加的字段。

#### 决定 4｜对象字段是"合并语义"，禁止向 `null` 写对象

**这是 2026-10-13 真实踩到的坑，直接导致线上 `ops.health` 返回 `INTERNAL`。**

云数据库的 `update` 对**对象字段采用合并语义**（不是整体替换）。因此：

```js
// ❌ 错误：先插 null，之后写对象 → 合并时去创建子路径
await repo.insert('x', { payload: null })
await repo.update('x', id, { payload: { ok: true, data: {...} } })
// → -502001 Cannot create field 'data' in element {payload: null}

// ✅ 正确：要么初始化成 {}，要么存 JSON 字符串
await repo.insert('x', { payloadJson: '' })          // 字符串
await repo.update('x', id, { payloadJson: JSON.stringify(obj) })
```

**内存仓储没有"合并语义"这个概念，所以这类缺陷本地测试永远测不出来。**

由此得出两条纪律：

| 纪律 | 说明 |
|---|---|
| **对象字段的初值用 `{}`，不用 `null`** | 例：`meet_tasks.linkToTrip` 初值为 `{}`；读取方判内层字段而非对象本身 |
| **整体替换的聚合体优先存 JSON 字符串** | 例：`operations.responseJson` 存 `JSON.stringify(response)` |

**验证手段**：`ops.selfTest` 会实测九种写入形态，把"能不能写"从推理变成测量。**新增写对象/数组的代码后，先跑一次它。**

#### 实测结果（2026-10-13，env = cloud1）

| # | 形态 | 结果 | 结论 |
|---|---|---|---|
| ① | `createCollection` | ✅ `created: true` | 集合必须显式创建；`add()` **不会**自动建集合 |
| ② | 读不存在的集合 | ✅ `count: 0` | 仓储层已归一化为空结果 |
| ③ | 删除文档 | ✅ | |
| ④ | 插入嵌套对象 + 对象数组 | ✅ | |
| ⑤ | **向已有对象字段写对象** | ✅ **合并语义** | 未提及的字段**被保留**（`{a:1,deep:{b:2}}` ← `{a:9,deep:{b:8,c:7}}` ⇒ `{a:9,deep:{b:8,c:7}}`） |
| ⑥ | **向 `null` 字段写对象** | ❌ `-502001` | **已知限制**，代码已规避（见上） |
| ⑦ | **整体替换对象数组（`trips.nodes` 形态）** | ✅ | **数组可直接用，数据模型无需改为 JSON 字符串** |
| ⑧ | **整体替换对象数组（`meet_tasks.participants` 形态）** | ✅ | 同上 |
| ⑨ | **乐观锁 `updateCas`** | ✅ `staleUpdated:0 / goodUpdated:1 / newVersion:2` | **旧版本号写入被拒且版本未被改动** —— §0 决定 2 的机制实测可用 |

**两条由实测得出的纪律**：

1. **对象字段无法通过 `update` 删除字段**（只有覆盖与新增）。需要清空时用专门的删除指令，不要以为写空对象就能清掉。
2. **判据看 `criticalFailureCount`，不是 `failedCount`**。`ops.selfTest` 把⑥归入 `knownLimitations`，
   因为它记录的是"我们主动避开的形态"，而不是"意外坏掉的形态"。两者混在一起会让结论失去意义。

> ⑨ 的结果直接支撑 10/24「旧版本确认不能使新方案生效」与 10/25「打开旧卡片不会执行旧方案」
> 两条验收 —— 它们不再只是设计文档上的一句话，而是有实测记录的机制。

### 1. 集合总览与关系

```text
users ──┬── crew_members ──┬── crews
        │                  ├── locations（高频写，短期保留）
        │                  ├── crew_messages（队伍文字聊天）
        │                  └── subscribe_intents（订阅意向：本人×队伍×类型）
        ├── requirements（个人 / 团队需求）
        ├── trips ──┬── trip_versions（版本快照）
        │           ├── change_proposals（变更提案 + 候选）
        │           └── meet_tasks（集合任务，引用 trip 节点）
        ├── operations（幂等记录）
        ├── privacy_consents
        ├── notice_log（通知去重与发送结果，dedupeKey 唯一）
        └── events / decisions（评测与可解释性，只增不改）

places ──┬── trips.nodes[].placeId          （内嵌引用）
         ├── meet_tasks.placeId / candidatePlaceIds[]
         └── requirements.structured.mustVisitPlaceIds[]
```

**内嵌 vs 引用**的判断依据是"是否总是一起读、是否有独立生命周期"：

| 数据 | 处理 | 理由 |
|---|---|---|
| `trips.nodes` | **内嵌数组** | 首版每次只处理未来 1–3 个节点，总量 ≤10；永远和行程一起读 |
| `meet_tasks.participants` | **内嵌数组** | 参与者 ≤10，确认状态与任务版本强绑定，必须原子更新 |
| `change_proposals.candidates` | **内嵌数组** | 候选是一次性产物，必须与该次提案同版本读；独立集合会产生孤儿候选 |
| 成员位置 | **独立集合** | 高频写、短期保留、清理策略与队伍数据完全不同 |
| 事件日志 | **独立集合** | 只增不改，量大，评测导出要全表扫描 |

#### 2.2.1 准入规则：**按用途分两级**（2026-10-13 修正）

首版把核验做成了"全有或全无"（`verifiedAt` 为空则连行程里都不能出现）。
**这是错的** —— 它会让地点检索回来的 POI 一个都用不了，与「外部检索保证覆盖度、
实地踏勘保证可信度」的设计目标直接矛盾。

行程节点与集合点都不要求实地核验。集合点可直接通过地图检索或手动选取。

| 用途 | 条件 |
|---|---|
| 行程节点 | 有名称和坐标 |
| 集合点 | 有名称和坐标；推荐时排除明确标记为不适合集合或低可信度的地点 |

`trip.plan.unverifiedNotice` 保留核验状态作为资料信息，`scope` 为 `sourceInfo`，不代表用途限制，界面不再显示“未核验就不可集合”的警告。

#### 2.2.2 核验状态仅作资料记录（2026-10-15 统一）

| 等级 | 判据 | 是否要求该状态才能集合 |
|---|---|---|
| `field-survey` | `verifiedAt` 非空 | 否 |
| `aggregated` | `meetingPointEligible === true` | 否 |
| `none` | 两者皆无 | 否 |

`verifiedAt` 和 `verificationLevel` 如实记录资料来源，不是集合前置条件。`meetingPointEligible === false` 表示明确不适合集合，推荐时排除；未设置该字段不构成拒绝理由。

`photos` 记录 `source`、`provider` 和 `verified`，网络照片仍按来源标记，不声称来自现场。是否有照片、是否实地拍摄均不影响集合点的使用。

#### 2.2.3 `place.survey`｜唯一的写入入口

`places` 集合**只由踏勘／核验写入**（2.2.1 的推论），所以必须有且只有一个写入 action。
仅 `dev` 环境可用（与 `ops.initDb` 同惯例）—— 这条数据是可信度层的输入，被污染后整套说法都不成立。

它保证的不是"字段写进去了"，而是**`canBeMeetingPoint()` 从此返回 true**。
这是两个不同的命题：`verifiedAt` 漏写、`confidence` 写错、坐标写成 `lat/lng` 而
`authz` 读 `latitude/longitude` —— 任何一条都会让记录"看起来录好了、推荐里永远不出现"，
**且不报错**。所以该 action 的返回值直接给出 `eligibility` 与一句人话说明。

| `ownerUserId`* | string | |

`structured` 结构：

```js
{
  startAt, endAt,                 // 时间约束（Date | null）
  startPlaceId,                   // 起点
  mustVisitPlaceIds: [],          // 必去
  avoidPlaceIds: [],              // 排除
  maxWalkMinutes, maxWalkMeters,  // 步行上限
  pace: 'relaxed' | 'normal' | 'packed',
  preferences: []                 // 软偏好：少走路 / 建筑 / 多拍照
}
```

`constraints[]` 结构 —— **这是 §6.2 约束分类的落地**：

```js
{
  key: 'endAt' | 'mustVisit' | 'maxWalkMinutes' | 'minStay',
  value,
  hardness: 'hard' | 'soft' | 'unknown',   // ← 三态，不可省略
  sourceMemberIds: [],                      // 团队时谁提的
  confirmedAt, confirmedBy                  // 硬约束必须有确认时间
}
```

**规则**：
- `hardness` 为 `unknown` 的约束**不得**被算法当作硬约束使用（§6.2：「有点累」不能自动转成步行上限）。
- 团队中多人硬约束冲突时，返回 `conflicts` 说明，**不自行取舍**（§6.2 末句）。
- 只有 `hardness === 'hard'` 且 `confirmedAt` 非空的约束参与可行性判定。

| `participants`* | array | 见下 |

| `allArrivedAt`? | Date | **② 实际全员到齐时间** |

`participants[]` 结构：

```js
{
  userId,
  status: 'invited' | 'confirmed' | 'declined' | 'arrived',
  confirmedVersion,      // ← 关键：确认时任务的 version
  confirmedAt, arrivedAt, declinedAt
}
```

**两条不可违背的规则**：

1. **三个时间必须是三个独立字段**。`plannedMeetAt` / `allArrivedAt` / `departedAt` 绝不合并，也绝不用「到齐时间」推断「离开时间」。理由见 §7.3：到齐后团队可能还要休息、买东西，混用会系统性低估延误并沿后续节点放大。
2. **`confirmedVersion !== meet_tasks.version` 的确认一律无效**。这是"旧版本确认不能使新方案生效"的直接实现：改地点或时间 → `version + 1` → 之前所有 `confirmed` 自动失效，需要重新确认。

状态机（`status` 取值）：

```text
proposed → confirmed → active → arrived_all → departed → completed
    └──────────────── cancelled ────────────────┘
```

联动规则（**写进代码，不靠注释**）：
- 进入 `arrived_all`（②发生）：只给出**预计**后续安排，**不改写路线**。
- 只有进入 `departed`（③发生）：才更新后续行程的可行性判断，并**一次性**提出调整候选。
- 不在每次位置更新时重排。

#### 2.11 `operations`｜幂等与并发控制　P0

| 字段 | 类型 | 说明 |
|---|---|---|
| `_id`* `requestId`* | string | **唯一索引**，客户端每次操作生成 UUID |
| `userId`* `action`* | string | |
| `targetType`? `targetId`? | string | |
| `status`* | string | `in_progress \| done \| failed` |
| `responseJson`? | string | **首次响应的 JSON 字符串**（不是对象 —— 见 §0 决定 4）。重放时 `JSON.parse` 原样返回 |
| `createdAt`* `finishedAt`? | Date | |

索引：`requestId`（唯一）、`createdAt`、`expiresAt`

**行为**：
- 同一 `requestId` 二次到达 → 直接返回首次结果，附 `replayed: true`，**不重复执行**。
- 首次执行失败 → **不缓存失败响应**，允许重试（否则一次网络抖动就永久锁死该操作）。
- `in_progress` 超过 **5 分钟**仍未收敛 → 视为卡死，放行重试，不永久阻塞（对应 11/11「超时」用例）。
- 在 5 分钟内的 `in_progress` → 返回 `RATE_LIMITED`，防并发重复执行。

覆盖 11/11「重复请求」与「超时」两个异常用例。

2026-10-15/16 例外：`speech.recognize`（旧一句话转写）与 `speech.session`（实时识别短期签名）均不写此集合、不缓存响应，避免持久化未提交文字或访问签名；客户端不自动重试。重复调用会重新识别/签发新 voice_id，不保证不重复用量。只记录不含音频、转写、URL 或签名的 API 状态事件；实时音频由小程序直接发送给腾讯云 ASR，不经 api 云函数、不存云存储。

2026-10-17 OCR 例外：`ocr.recognize` / `ocr.searchMeeting` 同样不写 operations，保证识别正文和附近候选不被持久化或在退出后重放。图片只在本次云函数与腾讯云 OCR 请求内处理，不进入项目业务库或云存储；事件只记状态、耗时和脱敏错误。新功能无新增集合；仅当用户确认选点并主动发起集合时，按既有任务结构保存名称和真实 POI 坐标，method 为 manual，不把外部 POI ID 写为已存在的 places 主键。

### 3. 错误码表（今天冻结，10/15 接口评审不再改）

**错误码是 B 的核心验收「遇到异常不会悄悄执行错误安排」的直接载体**，所以每条错误码都要说清"系统因此不会做什么"。

| `FORBIDDEN_ENV` | 在非 dev 环境调用初始化类接口 | 不建集合、不灌种子数据 |
| `FORBIDDEN_NOT_ADMIN` | 调用运维/探针接口但不在 `ZY_ADMIN_OPENIDS` 白名单里（**含白名单未配置**） | 不执行任何业务写入，但**照样写 events 留痕**（§11.3 要的就是这份"被拒"记录） |

### 4. 坐标系（10/14 验证核心）

**全库统一 GCJ-02**，每个含坐标的文档写 `coordSys: 'gcj02'`。

理由：微信 `map` 组件与 `wx.getLocation({type:'gcj02'})` 用 GCJ-02；高德/腾讯地图 Web 服务用 GCJ-02；百度用 BD-09。**混合坐标系会产生 50–500 米偏移**，在"景点内集合"这个尺度上足以让人走到马路对面。

10/14 验证清单：
1. 地图服务选哪家（高德／腾讯），Key 是否需绑定 IP 白名单或小程序 AppID。
2. 请求参数与返回字段：距离单位（米）、时长单位（秒）、步行路径数组格式。
3. 坐标系参数（是否可指定 `gcj02`），返回坐标是否与输入一致。
4. **失败情形**：超时、额度耗尽、起终点过近（<50 米）时的返回。
5. 免费额度上限与计费方式 → 记入成本表（11/12 验收）。

| 数据 | 保留 | 理由 |

| `locations` 精确坐标 | **短期**（建议 7 天，由 `expiresAt` + 定时清理执行） | 精确轨迹是最敏感数据 |

### 0. 为什么是"单一入口 + 内部路由"

微信云开发的默认做法是"一个功能一个云函数"。本项目**不这么做**，理由有三条，今天定死后不再讨论：

1. **共享代码无法跨函数复用**。开发者工具上传云函数时只打包该函数目录，上级目录的 `shared/` **不会**被带上去。若拆成 13 个云函数，要么每个目录里放一份副本（必然漂移），要么依赖云端 npm 安装（`file:` 本地路径在云端不存在，会失败）。单入口则共享代码就是同目录下的普通文件。
2. **契约只有一处**。响应格式、错误码、鉴权、幂等、日志集中在入口，A 只需要对接一种返回结构。
3. **统一配置入口函数超时**。在云开发控制台配置 `api` 的超时时间为 20 秒，provider 各自有请求超时。当前 `config.json` 不声明未经验证的超时字段，部署方式以 README 为准。

例外：定时清理位置需要一个独立的**定时触发器**云函数 `timer-cleanup`，它是唯一的多余函数。

### 1. 统一调用约定

#### 1.1 请求

```js
wx.cloud.callFunction({
  name: 'api',
  data: {
    action: 'trip.plan',           // 必填，域.动作
    requestId: 'uuid-v4',          // 必填，客户端生成，用于幂等
    expectedVersion: 3,            // ⚠️ 在**信封层**，不在 payload 里（见下）
    payload: { /* 动作参数 */ }
  }
})
```

`requestId` 由客户端生成（A 侧 `utils/api.js` 统一封装）。**服务端不生成**，否则重试无法识别。

#### ⚠️ 1.1.1 `expectedVersion` 在信封层，不在 `payload` 里

**这是本项目踩过的真实缺陷（2026-10-13），务必看清。**

```
data: {
  action, requestId,
  expectedVersion: 3,        ← ✅ 正确位置（信封）
  payload: { tripId, expectedVersion: 3 }   ← ❌ 写在这里会被**静默忽略**
}
```

**写错位置的后果不是报错，而是"版本校验恒等于通过"**：

| | 后果 |
|---|---|
| 服务端读 `ctx.expectedVersion` | 读不到 → 曾回落到"当前版本" → CAS 永远成功 |
| 于是「旧版本确认不得使新方案生效」（11/5 验收项） | **实际使用中完全没生效**，而所有测试都是绿的 |

现在的防护（两道，缺一不可）：

1. **服务端必填**：`trip.progress` / `trip.confirmChange` 缺 `expectedVersion` 直接返回
   `INVALID_PARAM`，**不再提供"没给就用当前版本"的兜底** —— 那个兜底正是失效的原因。
2. **客户端只有一个入口**：`utils/api.js` 的 `callApi(action, payload, options)`，
   版本号走**第三个参数**的 `options.expectedVersion`。页面里不要手写 `wx.cloud.callFunction`。

> 因此下表中凡涉及版本一致性的写操作，`expectedVersion` **不出现在 payload 列**，
> 一律走信封。别再照着"参数表里有它"去写 payload。

#### 1.2 成功响应

```js
{
  ok: true,
  data: { /* 动作结果 */ },
  meta: {
    requestId, serverTime,          // serverTime 为 ISO 字符串，客户端不得用本地时间做权威判断
    version,                        // 受影响对象的当前版本
    replayed: false,                // true 表示命中幂等，未重复执行
    durationMs
  }
}
```

#### 1.3 失败响应

```js
{
  ok: false,
  error: {
    code: 'VERSION_CONFLICT',       // 见数据模型 §3 错误码表
    message: '行程已被其他成员更新',   // 面向用户，可直接展示
    details: { currentVersion: 5 }   // 面向开发者，A 用它做恢复动作
  },
  meta: { requestId, serverTime, durationMs }
}
```

**云函数不抛异常给客户端**：所有异常在入口转为上述结构。`ok` 字段是 A 侧唯一需要判断的分支。

> **`place.search`：外部检索保证覆盖度，实地踏勘保证可信度。**
>
> ⚠️ **检索结果一律不入库**（2026-10-13 用户决定："以后地点不会入库，全从腾讯地图搜索"）。
>
> 问题不是"占空间"，而是：**"库里有这条"看起来像"我们确认过这个地方"**。
> 检索回来的是**未核验**的上游数据，与踏勘核验过的混在一个集合里，
> 准入分级（§5.3）就失去了依据。现在两条线各归各的：
>
> ```
> 检索线  place.search  → 候选（不入库）        保证覆盖度
> 踏勘线  places 集合   → 核验数据（只此一处）   保证可信度
> ```
>
> **接缝是"对上号"**：检索结果若与已踏勘的地点同名同坐标，
> 就带上库里那条的 `placeId`（`matchedSurveyed: true`），
> 于是自动获得核验待遇 —— 可作集合点、可用实测步行时间。
>
> · 每个候选都有 **`itemId`** —— **稳定标识**，与是否入库无关
>   （`placeId` > `poiId` > 名字+千分位坐标，见 `lib/place-id.js`）。
>   **必须稳定**：否则同一批地点两次检索得到不同的键，
>   踏勘实测的步行时间永远对不上、行程也无法复现。
> · `placeId` 只有在**对上踏勘地点**时才有值，否则是 `null`。
>   **没有它也照样能规划** —— 前端把地点数据内嵌传给 `trip.plan`。
> · 未踏勘的候选带默认停留时长（`visitDurationSource: 'default-untuned'`），
>   界面必须能看出那是估值。
> · **以 `poiId` 去重**：同一 POI 在不同关键词下只会出现一次（`foundBy` 记全部来源）。
> · `save: false` 只给候选不写库，此时 `placeId` 为 `null`。
> · **排序**：默认 **`basis: 'relevance'`——保留上游的相关性排序**。
>   2026-10-13 修正：首版默认按"到检索中心的直线距离"重排，**把上游的相关性排序
>   整个冲掉了**，导致搜「冰雪大世界」时结果前列全是附近的地铁站。
>   **搜索的第一诉求是"找到我要的那个地方"（相关性），距离是第二诉求。**
>   需要"离我最近"时传 `rankBy: 'distance'`；`rankBy: 'verified'` 则已核验优先。
>   距离仍照常计算并返回，只是不再当默认排序依据。
> · `enrichWalk: true` 时对前 `enrichWalkTop` 个调真实步行接口精排 ——
>   **直线距离在短距离下不可靠**（实测直线 10 米对应实际步行 76 米），
>   但每次会多消耗若干次地图配额。
> · **`scope`：默认 `'city'`（全城）**，需要"附近的"才传 `'nearby'`。
>   2026-10-13 修正：首版一律 `nearby(用户位置, 5000)`，后果是用户说
>   「我想去冰雪大世界」，而真正的冰雪大世界在松北区、离他十几公里，
>   **被半径排除在外** —— 系统在附近找了家同名的 VR 游戏店推荐给他。
>   **"找那个地方"与"找附近的地方"是两种检索。**
>   `centerUsed` / `regionUsed` / `scopeUsed` 必须回传，否则调用方会误以为
>   结果来自自己指定的位置。
>
> ⚠️ 上游字段名（POI 主键 `id` vs `_id`、坐标 `lat`/`lng`）**尚未实测确认**，
> 解析层两种写法都接受，并把实际命中的写进 `parsedVia`。首次真实调用后请核对。

##### 2.2.1 多关键词检索与自动预选（2026-10-13 新增）

用户一次可能说**好几个**地方，所以 `place.search` 接受 `keywords: []`：

- **逐个检索，轮转合并**。不能按关键词顺序拼接 —— 那样第一个词会把整个列表占满，
  第二个地方永远排在后面。这正是"用户说去冰雪大世界，看到的全是哈工大的各种门"的原因。
- 每个候选带 `foundBy: []`（被哪些检索词找到），界面能说清来源。
- `keywordsUsed` / `failedKeywords` **必须如实回传** ——
  哪个词没搜到要说出来，不能让用户以为系统找过了。

`autoPick` 给定时返回 `picked`，这是**"AI 生成路线"与"AI 帮你搜"的分界**：

| 规则 | 说明 |
|---|---|
| 每个点名的名字**只取一个最佳匹配** | 用户说的"冰雪大世界"是**一个**地方，不是十个命名含它的 POI |
| `bestMatch` 排序 | 名字恰好等于 > 名字含关键词 > **上游认定的模糊匹配** > "关键词+后缀"形态（科技园/校区/分店…） |
| **上游的语义匹配优先于自己的字符串规则** | 「哈工大」与「哈尔滨工业大学」对不上字符串，但上游认得 —— 不该用土规则去压它 |
| 连"必去"也要过 `visitable` | 交通设施、住宿（宾馆/民宿/公寓…）**再"必去"也不是游览地** |
| 点名 ≥2 个 → **只选点名的** | 用户已经排好了行程（"先去 A 再去 B"），多塞一个都是替他做决定 |
| 点名 ≤1 个 → 按节奏补足 | 轻松 3 / 正常 4 / 紧凑 5 |
| `keywordsMissing` | 哪个词没选上如实列出 |


#### 2.3 需求与规划

| Action | 入参 | 出参 | 说明 |
|---|---|---|---|
| `req.submit` | `{scope, rawText, structured, constraints[], crewId?}` | `{requirementId, conflicts[]}` | 规划接口，当前未注册；实际需求提交走 `intent.parse` |
| `intent.parse` | `{text, crewId?, startPoint?, preferModel?}` | `{ok, requirementId, parsed, structured, constraints, explanation, uncertainties, searchKeyword, searchKeywords[], parser, degraded, attempts, promptVersion, model}` | **一句话 → 结构化需求**，见下方 |
| `trip.plan` | `{places[] \| placeIds[], startAt?, constraints?, startPoint?, stayMin?, stayByText?, strategy?, crewId?}` | `{tripId, version, nodes[], feasible, conflicts[], unverifiedNotice, walkTimes, startPoint, startLeg, summary}` | 生成行程。**地点数据可内嵌**（检索结果不入库），见 §2.3.4 |

> **`intent.parse`：AI 层与算法层的接缝。**
>
> 解析器是**可替换的 provider**（与地图服务同一模式），带**必然有结果的降级链**：
>
> ```
> 模型（配了 AI_API_KEY）──失败──▶ 规则解析 ──▶ 一定有结果
> ```
>
> 依据是 §6.5 最后一句：「**模型不可用时，保留手动修改与确定性可行性检查。**」
> 降级**必须留痕**（`attempts` / `degraded`），不能让人以为这是模型解析的结果。
>
> 三条不许越过的线：
> 1. **原话原样落库**（`rawText`）—— 附录 C 的评测与可解释性都靠它；
> 2. **含糊表达不得换算成数值**（§6.2）——「有点累」进 `uncertainties`，
>    绝不变成 `maxWalkMinutes: 30`；宁可少一个约束，不用猜的数值算可行性；
> 3. **降级留痕** —— `parser` / `degraded` / `attempts` 随结果回传。
>
> 环境变量：`AI_API_KEY`、`AI_BASE_URL`（默认 DeepSeek）、`AI_MODEL`。
> 走 OpenAI 兼容协议，换模型只改环境变量。提示词版本 `PROMPT_VERSION` 随结果回传，
> 附录 C 的评测要能说清"这个分数是哪一版提示词跑出来的"。
> `temperature: 0` —— 解析要**可复现**，随机性会直接污染评测分数。

##### 2.3.1 提示词 schema 与解析器的期望必须一致（2026-10-13 记录）

**改了提示词就必须改 `PROMPT_VERSION`**，且 schema 的字段必须覆盖
解析器真正读取的每一个。今天连踩两次：

| 现象 | 真正的问题 |
|---|---|
| 「玩一小时」被整个丢掉 | schema 里**没有** `stayMinutes` |
| 三个不同时长接不住，模型反过来问用户 | schema 里**只有一个** `stayMinutes`（缺 `stayMinutesByText`） |

**听不懂是模型的问题；听懂了接不住，是 schema 的问题。**

现有测试把"提示词声明的字段"与"代码真正读取的字段"**钉在一起**，
以后漂移会直接测试失败。

另外两条提示词纪律（都是实测踩出来的）：

- **"没说" ≠ "不确定"**。用户没提到出发时间/节奏是**正常情况**，不必报告 ——
  首版让它报，界面上全是废话待确认项，真正的待确认被淹没。
- **`anchorText` 只用于"一片区域"**（「中央大街附近逛逛」）。
  具体目的地填在这里会让系统以为用户在"随便逛"，从而**自作主张多加地点**。

##### 2.3.2 按地点分别设停留时长

```
stayByText: { "哈工大": 60, "冰雪大世界": 120, "哈学院": 60 }
```

优先级：**按地点给的 > 统一 `stayMin` > 地点自带 `visitDurationMin.default`**。

- 匹配用**双向包含**（用户说「冰雪大世界」，POI 叫「哈尔滨冰雪大世界」要能对上）；
- **匹配不上就用默认值，绝不用别的地点的时长顶替** ——
  否则"哈工大 1 小时"会让"冰雪大世界也 1 小时"。

##### 2.3.3 `ai.probe` —— 大模型接口探针

与 `map.probe` 同一个套路：**不猜，实测**。四个用例：

| # | 用例 | 期望 |
|---|---|---|
| ① | **真实调用**：一句话 → 结构化需求 | 关键用例；带解析结果、**原始返回**、耗时、token 用量 |
| ② | 无效 Key | **期望失败** —— 确认鉴权失败被识别为失败，而不是被当成"模型没理解" |
| ③ | 未配置 Key | 期望失败 —— 确认给出可执行的修复指引 |
| ④ | 规则解析对照 | 信息项 —— 同一条话不用模型会得到什么，两种解析的差距一目了然 |

判据只看 ①。**仅在 `dev` 环境开放**（会产生真实费用）。
Key 只以掩码出现，绝不进响应。

##### 2.3.4 地点数据可以内嵌（因为检索不入库）

```js
trip.plan({
  places: [                       // 检索结果直接传进来，不必先入库
    { name, location, category, poiId?, placeId?, visitDurationMin? }
  ],
  // 或沿用 placeIds（库里踏勘核验过的地点）；两者可同时给
  startAt, constraints, startPoint,
})
```

**顺序只由数组次序决定** —— 不按对象键顺序（那在 JS 里不保证，
会让游览顺序随机漂移）。

`_id` 由 `lib/place-id.js` 的 `stablePlaceId()` 合成，**必须稳定**：
同一批地点两次规划要得到相同的键，否则踏勘实测的步行时间
（`walkableTo` 按它索引）永远对不上。

**行程节点自带"地点快照"**（`nodes[].placeSnapshot`）。原因是
`trip.adjust` 原先回库按 `placeId` 读地点 —— 不入库之后读不到了。
节点自带快照，行程就**自洽**：

> **自洽的记录才可复现。** 这与"行程自带约束快照"是同一个原则
> （docs/项目计划书.md#data-model：adjust 不依赖原始需求，11/5 固定测试集要能完整复现）。

**代价（已与用户确认）**：步行时间缓存对检索来的地点**失效** ——
每次规划重新调地图接口。5 段行程 ≈ 5 次调用；
免费额度 6000 次/日，量级上完全够。
`walkTimes.mapApiCalls` 会如实反映这个数字变大。

##### 2.3.5 路线预览与地图导航（`trip.legRoute`）

2026-10-18 已扩展为步行、骑行、驾车、公交和地铁。所选方式决定查询接口，失败明确提示原因和重试入口，不用步行替代其他方式。各方式在地图返回的有效方案中按总耗时取最短路线；驾车请求明确指定 `LEAST_TIME`，公交采用高德 v3 最快捷策略，地铁在含地铁方案中取总耗时最短的一条，方案仍可能包含公交接驳，界面按实际组成标注。地图耗时是预测值，不是现场实测或未来到达保证。

| 方式 | 接口与返回 |
|---|---|
| 步行 / 骑行 / 驾车 | 腾讯 `direction/v1/walking`、`bicycling`、`driving`，压缩折线及转向指引；骑行/驾车 duration 按官方分钟单位处理 |
| 公交 / 地铁 | 高德 `v3/direction/transit/integrated`，哈尔滨 city=0451；duration 秒转分钟；总耗时含步行接驳与换乘 |

`mode` 可显式传入，缺省使用目的站的计划方式；其余入参含 `tripId`、可选 `nodeId`、`fromPoint`，信封携带 `expectedVersion`。响应含 mode、provider、distanceMeters、durationMinutes、transit 摘要、route 和 mapApiCalls。请求前后检查权限和行程版本，防止旧进度路线回填。

- 起点优先级为有效当前位置、目标前最近的已到达/完成站、保存的出发位置；都缺失或起终点重合时明确说明。
- 腾讯折线首对为绝对纬经度，其余为 1e-6 度增量；转向文字直接取上游 instruction。公交把上游站名、线路方向、途经站和出入口整理为步骤，同一段的备选线路不当作连续换乘。
- 公交分别绘制步行接驳和乘车折线，缺失或非法路段不补直线；无路径时仅保留起终点及已有指引。包含暂不支持的铁路/出租车接驳时明确引导打开地图查看完整路线。
- 完整几何仅在主动查看路线时解析，不塞进日常规划快照。计数按 provider 实际 requestCount，未配置 Key 或方式不支持时为 0。
- 选择器应用方式通过 `trip.adjust` 在原行程上生成候选，`autoApply: never`；确认后重算后续到达时间，保留已完成记录。仅复用起终点未改变的旧候选作为参考；本次路线查询时长单独展示，不暗中覆盖行程时间。
- 当前目标、方式或版本变化后旧路线失效；到达、完成、跳过后切换到下一站，全部走完则收起路线。迟到响应不能恢复已退出或旧目标路线。

页面的“查看路线”用于静态预览和指引，不做连续 GPS、偏航重算或实时语音。“打开地图导航”调用 `wx.openLocation`，只传递目的地，用户须在打开的地图中选择对应方式并启动导航；不保证外部地图会沿用本页路线。

部署需更新完整 api 与小程序，沿用 MAP_KEY、AMAP_KEY，无新增集合。腾讯骑行/驾车服务权限、高德线路可用性、公交几何和微信手机展示仍须真实环境验收。接口依据：[腾讯路线服务](https://github.com/TencentLBS/tencentmap-webservice-skill/blob/main/references/api-direction.md)、[高德 v3 路径规划](https://lbs.amap.com/api/webservice/guide/api/direction)。

> **`startPoint`（出发位置）**：给定时**第一段交通从那里算起**，响应回传 `startLeg`
> （`{minutes, meters, source, toPlaceName}`）。前端默认传用户当前位置。
> 不给的话，行程会假装人已经在第一个景点门口 —— 计划出发时间、总步行量与
> "能不能赶上结束时间"都会偏乐观。
> 起点是**移动的**，所以不进 `place.walkableTo` 缓存（缓存是地点↔地点的）。

> **调整分级（2026-10-13 决定）**：`trip.adjust` 默认 `autoApply: 'whenNoTradeoff'`。
>
> | 情况 | 行为 |
> |---|---|
> | **个人模式 + 唯一可行候选 + 没有牺牲任何安排** | **直接生效**（`applied: true`），走的是正式确认路径，不是旁路 |
> | 用户明确缩短一站停留，候选恰好按输入减时且不低于地点建议下限，无额外改动 | 个人模式唯一可行候选直接生效，返回实际前后时长 |
> | 出现额外取舍（额外压缩、删除节点或停留低于建议下限） | 返回候选，等 `confirmChange` |
> | **团队模式** | **一律确认**（§8.1 成员确认是核心卖点，不能被简化掉） |
> | `autoApply: 'never'` | 保持严格：一律返回候选等确认 |
>
> 判据使用 `impact.removedNodeIds` 与 `shortenedNodeIds`：按用户输入恰好缩短的目标节点不算额外取舍，但低于建议下限、缩短到零或被进一步压缩时仍需选择。`impact` 保留完整改动记录，`tradeoff.shortened` 只计需要再次选择的压缩，`requestedShortening` 标识已明确要求的减时。
> 每个候选都带 `tradeoff` 与 `requiresConfirmation`，写入提案与返回值一致；团队与 `autoApply: 'never'` 始终要求确认。页面自动滚动到待选方案，并说明尚未生效。

> **`unverifiedNotice`（未核验地点标注）**：非 null 表示本次路线含未核验地点。
> `scope: sourceInfo` 仅表示资料状态。集合点可直接通过地图搜索或手动选择，无需实地核验；不显示核验前置条件警告。准入规则见 `docs/项目计划书.md#data-model §2.2.1`。

> **`trip.adjust` 的 `trigger` 就是 AI 层要生成的 function calling schema**：
> 类型见 `lib/planner.js` 的 `applyTrigger`（`extend_stay` / `shorten_stay` / `skip_node` /
> `replace_node` / `change_end_time` / `manual_progress`）。
> 当前行程页面用手动按钮生成同样的 trigger —— **AI 接入时只需换掉输入来源，接口与页面都不用改**。

### 3. 关键接口的语义约定（比字段更容易出错）

以下五条是评审最容易产生分歧的地方，今天先写死：

1. **`trip.adjust` 不改数据**，只产生 `change_proposals`。生效的唯一路径是 `trip.confirmChange`。这样"候选展示"与"方案生效"在接口层就是两件事，不会出现"点了调整就偷偷改了"。

2. **`feasible: false` 是正常业务结果，不是错误**。`INFEASIBLE_HARD_CONSTRAINT` 通过 `data.conflicts` 返回，HTTP/云函数层仍是 `ok: true`。零候选时 `candidates: []`，**不补默认方案**。

3. **`meet.arrive` 与 `meet.depart` 严格分离**。前者写 ②，后者写 ③。任何"用 `allArrivedAt` 当作离开时间"的写法都是 bug（§7.3）。

4. **所有涉及改地点/改时间的 `meet.*` 写操作必须带 `expectedVersion`**。版本不匹配 → `VERSION_CONFLICT`，且服务端**不得**把参与者的 `confirmed` 状态继承到新版本。

5. **`loc.*` 与路线解耦**。位置接口不触发任何行程重排。唯一的联动入口是 `meet.depart`。

### 二、标签口径（**这一节是本节的重点**）

| `straightMeters` | 两点的**直线距离** | 特征 | 真实几何量 |

### 三、评测器做了什么

#### 3.1 切分：**按路线组**，哈希确定性

> **⚠️ 2026-10-15 修正（本文档第一版写错了）**：第一版按每条样本的 `_id` 切分。
> 而同一路线会被反复调用，**近乎相同的样本会同时落进两侧** → 分数偏乐观且不报错。
> 现在按**路线组**切：同一条路（含**反向**、含**重复请求**）整体落一侧。
> 完整说明见 **`docs/项目计划书.md#datasets`** 第四节。

```
routeGroupId = sorted(端点键A, 端点键B).join('|')     ← 排序 ⇒ A→B 与 B→A 同组
frozen       ⟸  hash32(seed + routeGroupId) % 1000 < ratio*1000
dev          ⟸  其余
算不出组      →  ungrouped（**不进任何一侧**）
```

- **不用随机数**：每次跑得到不同划分，会让"这版比上版好"里混进切分噪声。
- **不按顺序切**：样本按时间写入，取前 N 条会把**同一时段整批**放进同一侧。
- **重复请求同组**：同一条路调十次 = 十条记录、**一个组**；统计时
  "记录数"与"独立路线数"**分开报**。
- 同一批数据 + 同一个种子 → **每次同一个冻结集**（有测试守）。

#### 3.2 拟合：**只许看开发集**

`fitConstant` / `fitBuckets` 只接受 `split.dev`。冻结集**只在最后打分时出现一次**。

> ⚠️ 泄漏的表现不是报错，而是**分数变好**。所以测试断言的是
> "**把冻结集标签改成离谱值，拟合出的系数必须一模一样**" ——
> 只断言"分数在动"是抓不住泄漏的。

#### 3.3 打分：中位数，且带符号

| 指标 | 定义 | 为什么 |
|---|---|---|
| `mapePercent` | **中位数**绝对百分比误差 | 一条上游异常值能把均值拉走；"中位差 12%"能拿去答辩，"均值差 340%"不能 |
| `biasPercent` | **带符号**的中位相对误差 | 只说"差多少"不够；"系统一贯高估 20%"才能指导修改 |

#### 3.4 判决：三个出口必须分得开

| 出口 | 含义 |
|---|---|
| `null`（真的打败了） | 更准，**且**相对改进 ≥ 阈值 |
| `NOT_BETTER` | 更差或持平 |
| `GAIN_BELOW_THRESHOLD` | 确实更准，但好得不够（可能来自切分噪声） |

**"没打败基线"与"样本不够，无法判断"是两句不同的话**，不合并。

### 四、门与阈值（**必须冻结**）

| 参数 | 值 | 性质 |
|---|---|---|
| `MIN_SCORE_SAMPLES` | 30 | 冻结集**记录数**下限："能号称跑过一次评测"的最低限度，**不是功效分析结论** |
| `MIN_SCORE_GROUPS` | 20 | 冻结集**独立路线数**下限（2026-10-15 加）—— 同一条路调三十次是**一条**路线，重复不提高信息量 |
| `MIN_BUCKET_SAMPLES` | 5 | 沿用 `ops.walkStats` 的口径：不足就不给系数 |
| `MIN_RELATIVE_GAIN` | 5% | **人为设定**，用于防止"改进 0.3% 就宣称胜利"；正式实测前冻结（§11.4） |
| `PRODUCT_CONSTANT` | 1.3 | 产品现状（对照基线之一） |
| `MAX_PLAUSIBLE_RATIO` | 20 | 写入侧的质量门：超过就标 `pending_review`（实测真实极值是 7.6，阈值必须远大于它） |

> 低于门时**分数一律为 `null`**，"不给一个看起来很精确的小数"，
> 并说清卡在**记录数**还是**独立路线数**。

### 八、明确不做（避免下一次又从头讨论）

| 不做 | 为什么 |
|---|---|
| **位置纠偏**（CNN-1D / 时空 3D 卷积） | 需要**历史轨迹**，而轨迹来自真实出行 → 无外场即无数据（§1.3） |
| **地图瓦片可达性**（CNN-2D / FCN） | 需人工标注瓦片，成本本届无法承担 |
| **集合点排序**（GNN）、**停留时长**（RNN） | 需要"哪次集合成功了""行程真的走完了"的标注 → 同上 |
| 用模型替换已跑通的规则 | §6.8.7 第 1 条：规则是**已经拿到的分数**，模型只做**增量** |

**关于 CNN-3D**：把「时间 × 经纬度」栅格化成体素做三维卷积，
在问题定义上属于**位置纠偏**的一种网络形状（与 CNN-1D 解决同一件事，只是把空间也做成卷积维度）。
它同样依赖历史轨迹 → **本轮不做**；若日后恢复外场实测并攒到轨迹，它是该问题的**首选候选**。

### 三、路线样本（`walk_samples`，schemaVersion **2**）

#### 3.1 字段口径（新旧对照）

| 新名 | 旧名（兼容，双写） | 是什么 | 能不能当标签 |
|---|---|---|---|
| `providerRouteMeters` | `actualMeters` | **地图返回的路径距离** | ✅ **本轮参考标签** |
| `providerDurationSeconds` | `predictedMinutes` | 地图**预测**耗时（秒） | ❌ **特征**（拿它当标签是循环论证） |
| `observedDurationSeconds` | `actualMinutes` | 真人观测用时（秒） | ✅ 标签，**没有就留空** |

> `actualMeters` 这个名字会误导（听着像"真人实际走的距离"，其实是地图路径距离）——
> 所以要改名，并**双写过渡**：读的一方两种都读（`lib/walk-eval.js` 集中处理）。

#### 3.2 一条必须写下来的偏差：命中缓存不产生样本

样本**只在真的调了地图接口时**才记。命中 `walkableTo` 缓存的段**不产生样本** →
样本集**系统性偏向"没缓存过的路线"**（新路线、跨区路线）。

这不是缺陷（缓存本来就是对的），但它是**抽样偏差**：
"我们有 300 条样本"不等于"覆盖了 300 段路"。
`cacheHit` 字段恒为 false，它存在的意义是**让这件事可被核对**。

> 这条是被测试逼出来的：有一条测试本来假设"重复规划会产生新样本"，
> **第一次跑就红了** —— 红的不是实现，是那个假设。

#### 3.3 采样要求（不追求条数，追求覆盖）

- 覆盖**六个距离区间**（0–100 / 100–300 / 300–600 / 600–1000 / 1000–2000 / 2000+）。
- 覆盖不同街区、入口与绕行条件。
- **重复请求留作稳定性记录，但不算新的独立路线。**
- 冻结**清单 + 切分结果 + 数据版本**（见第五节），只固定随机种子**不够**。

#### 3.4 输入契约（决定成败的边界）

若模型的用途是「**地图接口失败时兜底**」，那么在地图失败那一刻，
路径距离、预测耗时、路线形状**统统拿不到**。因此：

| | 内容 |
|---|---|
| **标签** | `providerRouteMeters`（离线训练时可以用） |
| **允许的输入** | `straightMeters`、`mode` |
| **禁止作为输入** | `providerRouteMeters`、`providerDurationSeconds`、`provider`、`routeGroupId`、`polyline`、`steps` |

首版**只用直线距离**：不塞天气、星期、时段 —— 它们要么拿不到，要么需要用户额外说。
有测试守着这条契约（把除 `straightMeters` 外的字段全换掉，预测必须不变）。

### 四、切分口径（这是 2026-10-15 修掉的那个真实缺陷）

#### 4.1 缺陷

原先按**每条记录的 `_id`** 哈希切分。而同一路线会被反复调用：
一次规划 5 段、十次规划就有十条同一路线的记录 ——
这些**近乎相同的样本会同时落进开发集与冻结集**：

> → 冻结集里"见过"的东西，参数已经在开发集上调过了；
> → **分数偏乐观，而且看起来一切正常。**

AI 样例同理：同一场景的**改写句**、同一段**多轮对话**若跨侧，
等于"训练时见过近似答案"。

#### 4.2 修法

```
① 每条记录算出一个 groupId（路线组 / 场景组）
② 按 hash(seed + groupId) 决定**整组**去哪一侧
③ 组内不允许跨侧 —— 有断言守着，分析时再独立验一次
```

三个细节，每一个都对应一类被堵住的泄漏：

| 细节 | 为什么 |
|---|---|
| **反向是同一组** | A→B 与 B→A 是同一条路，组键**排序后**拼接；否则同一条路被当两条独立路线，漏掉一半泄漏 |
| **重复请求同组** | 同一条路调十次 → 十条记录、**一个组**；统计时"记录数"与"独立路线数"分开报 |
| **算不出组的进 `ungrouped`** | 不塞进任何一侧 —— 让"身份不明"的东西参与评分是不可接受的 |

#### 4.3 两道门（缺一不可）

| 门 | 阈值 | 含义 |
|---|---|---|
| 冻结集**记录数** | ≥ 30 | 有得算 |
| 冻结集**独立组数** | ≥ 20 | 算出来有意义（重复请求不提高信息量） |

低于任一门 → **分数一律为 `null`**，并说清卡在哪一条。
"没打败基线"与"样本不够，无法判断"是**两句不同的话**。

#### 4.4 冻结清单的四个要素

只固定随机种子不够：数据一变，同一个种子算出的划分就不同，
于是"上个月那条基线是在哪一批数据上跑的"说不清。清单里必须同时冻结：

```
① datasetVersion  数据版本
② sourceSha256   源文件内容哈希（改一个字就变）
③ groups[]       切分**结果本身**（每个组去哪一侧），不是"用什么规则算的"
④ params         种子、比例、规则、门限
```

**已存在的清单默认拒绝覆盖**（要覆盖必须显式 `--force` 并留档旧清单）——
冻结的东西能随手改掉，就不叫冻结。

### 五、团队流程回放案例（`data/team-replay/`）

每个案例五段（设计稿）：

> **初始状态 → 操作序列 → 预期状态 → 必须始终满足的规则 → 实际执行记录**

- 六类优先情况：到齐未出发 / 延误导致超时 / 二次修改继承 / 旧版本确认 / 成员退出与位置过期 / 地图或 AI 失败。
- **不预填执行结果**：`executionRecord` 与 `recordedAt` 一律 `null`；
  预期状态是**设计意图**（措辞用"应"，不用"已"）。
- **不虚构数字**：不写"集合耗时 3.2 分钟"这类还没有的数据。

#### 5.1 证据分级（必须分别报告）

| 级别 | 能证明 | **不能**证明 |
|---|---|---|
| `synthetic` | 逻辑与状态流转 | 任何真实世界的量与效率 |
| `replay` | 用真实返回/真实状态回放的一致性 | 真实用户的体验 |
| `indoor_device` | 两台设备之间的状态同步流程 | **真实步行时间、集合效率、到齐与出发的时间差** |

> **室内点击「已到达」可以证明状态流转，不能证明真实步行时间或集合效率。**
> 三种级别**分别报告**，不得合并成一个"验证通过"。

#### 这一阶段真正要验的一件事（§7.3 的贡献点）

> **全员到齐 ≠ 已经出发。**

| 时刻 | 什么时候写入 | 到齐时会不会被改写 |
|---|---|---|
| ① 计划集合时间 | 发起集合时 | **不会** |
| ② 实际到齐时间 | 最后一人点「我已到达」 | — |
| ③ 实际出发时间 | 发起人点「确认现在出发」 | — |

**判据**：② 出现的那一刻，**行程版本不变、节点时间不变**；只有 ③ 之后才更新后续安排。
如果不满足，那就是 **§15 风险 #8「到齐与出发被混为一谈」**真的发生了 —— 这是要记录的一等素材。

**顺手拿一个真实指标**（附录 C.3 ③ 要的）：

| 项 | 记录 |
|---|---|
| 计划集合时间 | |
| 实际到齐时间 | |
| 实际出发时间 | |
| **到齐 → 出发的差值** | ______ 分钟 |
| 集合总耗时（发起 → 出发） | ______ 分钟 |

| 能证明 | 不能证明 |
